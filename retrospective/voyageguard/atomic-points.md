# VoyageGuard 原初想法 · 原子点

**输入**：`seed.md`（写 PRD 之前的想法，本人确认）
**用途**：链条跑完后逐条对照——最初的主张守住了几条、被改了几条、**新增了什么**
**隔离**：拆解、复核、三向审计均由独立 agent 完成，全部没见过成品与返工清单

---

## 一、判定规则

**四态**，不是两态：

| 态 | 什么时候用 |
|---|---|
| **守住** | 方案满足这条 |
| **收窄/变形** | 守住了，但范围、条件或形态被改了。**必须写一句「改成了什么」** |
| **未守住** | 方案违背这条 |
| **判不动** | 方案里没有可判的信息 |

**每条判定必须附方案里的原句 + 所在章节。没有引文的判定不计入统计。**

落在「原文留白」里的差异**不算偏离**，记为「原文未定，实现时才定的」。

## 二、原子点（14 条，P5 拆为 5a / 5b）

| # | 原子点 | 原文依据 |
|---|---|---|

| P2 | 评估对象是**一次有起讫的出行**，不是一个地点的天气 | 「缺一个能评估『点对点行程气象风险』的工具」 |
| P3 | 成品自己声明要解决的问题，仍是「看不懂 / 不知道标准 / 做不了决策」，**没有被换成别的问题** | 「卡在三个地方：看不懂、不知道标准、做不了决策」 |

| P11 | MVP 五项减法：不推送、不 RAG、不 LangChain、**纯 HTML/CSS/JS 单文件**、无登录 | 「目前只做 MVP，轻量化：……」 |
| P12 | 时间范围落在**未来短期若干天**——不做长期，也不能退化成只报当前实况 | 「只支持未来几天」 |

| P14 | 行业红线规则**内置在提示词里**，不放外部知识库/检索层/独立规则数据层 | 「不用 RAG（**规则量很小，直接写进提示词**）」 |

## 三、判据边界（防止事后误判，必须随表一起发给复核者）

- **P1** 只管坐船场景。同时用到温度/降雨/平均风速**不算破**；只在字段表里列出、判断规则里没用到，**算未守住**（判「判据」，不判「取数」）
- **P2 不管沿途** —— 那是留白第 1 条。既不能拿它要求覆盖沿途，也不能拿它判定「只许看起点终点」
- **P3** 只看方案的问题定义/背景章节怎么写，**不看功能覆盖**。功能覆盖由 P6 / P7 / P8 判。P3 与它们不互相推导、不重复计数
- **P5a / P5b 分别判**。P5b **只看有没有收窄表述**（「仅支持主要机场/主要港口」之类）；方案对数据覆盖只字不提**不算破线**。不判某个偏远地点实际取不取得到数据（留白 4）
- **P6** 不判红线的出处与权威性，**不判比对发生在提示词还是代码里**（留白 3、9）
- **P7** 只判「有没有那句判断」。旁边同时挂评分**不算破**；只给风险分数/等级、没有一句正面回答走不走，**算未守住**。中间档（有风险/待观察）不判违规（留白 5）
- **P8** 只判「有没有把专业量说成人话」，不判文案质量高低、不判要不要附原始数据
- **P9** 只判「有没有给」，**不判「什么时候给」**（原文没设「仅当不能走时」的前提，留白 7）。指向具体动作或时间窗的算（改签、换日期、提前一天走）；「请继续关注天气」这类不算。**不判备选该是哪一类**（留白 7）
- **P10** 判的是「那句判断正面回答的是不是这两个问题」。P7 判有没有判断、P9 判有没有备选。**三条命中同一处文本时只记一次，记在 P10**。船飞两半分别判，一半不成立整条不成立
- **P11 逐项判**，任一不成立即整条不成立。产品面两项（推送、登录）**方案没提视为没做（守住）**；技术三项（RAG / LangChain / 单文件）若方案整体不涉及实现，**整条记「判不动」**。只判 MVP 范围内，写进「后续 / V2」的不算破线（留白 14）
- **P12 不判具体天数**。逐日预报无论 3/7/10 天**都不算破线**；按周/月/季的长期展望算往长期；只给当前实况、没有未来时段算退回实况。**输出里同时呈现当前实况不算破**——P6 要的输入本来就是实时数据
- **P13** 只判「有没有一个自己写的 agent 循环」，不判循环几步、怎么编排、用不用工具调用
- **P14** 只判「规则放在哪儿」，**不判「比对判断在哪一层发生」**（留白 9）

## 五、原文留白（如实登记，不补成主张）


1. **沿途气象是否纳入（最要紧的一条）** ——原文只说「点对点行程」，提出者确认当时**并没有考虑过**途经地点有没有风险。这既不是「要做」也不是「决定不做」，是空白。任何一个方向的范围声明都不能记在原初想法头上。这条最锋利的边在于中间形态：**联程与中转**（飞机在第三地转机、船中途停靠）、**往返行程**——中转地算起讫还是算途经，原文同样一个字没有，落在同一片空白里。对应判据见 P2，P2 明确声明本条不管沿途。

2. **支持未来几天** ——原文写的是「未来几天」，没有定死天数，提出者确认当时并没有明确。对应 P12：只判方向，不判天数。

3. **「行业安全红线」的具体内容全部空白** ——红线从哪来、由谁认定、船和飞机各自看哪些量、阈值是多少，原文一个字没提，只说要「自动比对」。

4. **气象数据来源空白** ——用哪家数据、是否付费、偏远地区（比如弗洛雷斯这类地方）能不能取到数据，都没说。

5. **「能不能走」的结论形态空白** ——是「能走/不能走」两值，还是带中间档（有风险/待观察），原文没写。所以不能拿 P7 去判中间档违规。

6. **除浪高和阵风外还要不要别的量** ——能见度、雷暴、结冰等等没说。原文只是用浪高和阵风举了例，没有声明「决定量就是这两个」。所以 P1 只判「有没有这两个」，不判「有没有别的」。

7. **备选方案具体指什么没定义** ——飞机场景提到了「改签或做备选安排」，船的场景没有对应说明。另外，**备选方案是不是只在「不能走」的时候才出现，原文也没写**：原文把它无条件地挂在结论上，但没交代结论是「能走」时给什么。P9 因此只判「有没有给」，不判「什么时候给」。

8. **用户怎么输入行程没说** ——搜地名、选航线、填航班号、地图点选，一种都没提。所以任何一条判据都不能预设某种输入形态。

9. **「自动比对」由哪一层落地没说清** ——「规则写进提示词」「Agent 循环手写」这两项原文已交代，**已分别立为 P14 / P13**。本条剩下的空白只有一块：**比对判断本身**是提示词里的规则加大模型判断，还是确定性代码算，原文没说。

10. **判断出错怎么办** ——要不要免责声明、准确性责任如何交代，原文没有涉及。

11. **语言与地区** ——原文场景在葡萄牙，但没说产品面向哪个语言、哪个市场。

12. **起点故事里那段「没有订票平台、只能 WhatsApp 联系船长」** ——原文当作背景描述，没说产品要不要管订票或联系船长这一段，留白。

13. **「实时」到什么程度没说** ——多久刷新一次、能容忍多旧的数据，都没交代。

14. **MVP 之后的路线没说** ——被排除的推送提醒、RAG、LangChain 等等，是永久不做，还是后续版本再做，原文没有交代。原文只声明了「目前只做 MVP」。

15. **交通方式是不是只限船和飞机** ——原文点名了海岛船只通航和民航航班，又说「从偏远地区到大城市之间的常规出行都能覆盖」。火车、大巴、自驾算不算，没说。P5 不判船和飞机之外的交通方式；P5 判什么见判据边界。

16. **专业从业者能不能用** ——原文关于用户只写了普通游客「既不会查，也看不懂」这一句能力描述，既没说要服务船长、签派、调度这类懂行的人，**也没有任何排除他们的表述**。两个方向都不能替原文补。（原稿 P4 曾把「不是懂行的船长或飞行签派」写成原文主张；P4 后因与 P7/P8 重合、且系由描述句推成规范句而删除。本条留白独立成立，与 P4 在不在无关。）
