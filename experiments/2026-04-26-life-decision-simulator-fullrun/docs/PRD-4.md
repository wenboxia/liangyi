## §4.2.6 Onboarding 三屏内容（新增子节）

**章节位置说明**：作为 §4.2 关键页面信息层级的新子节，紧跟 §4.2.1 落地页之后逻辑顺序。

**voice 纪律**（继承 PRD-3 全文档）：禁用"被迫 / 必须 / 强制 / 强大 / 智能"等强迫感或炫技词；Skip 按钮在每屏右上角始终可见（承接 §3.5.4"未决定也可以"的精神）。

### 屏 1 · 产品 identity

**这屏想做什么**：用钩子"看见你没走的那条路"立产品身份；不堆术语、不立刻讲"和 ChatGPT 的区别"（那是 FAQ 的事）；让用户在 5 秒内理解"这是个陪我理一遍纠结的产品"。

**视觉重心**：占据中心的大镜子，镜面呈现柔焦水波 / 微折射，镜中模糊地映出一条蜿蜒的路（不具象、不暗示具体场景）。镜子边缘微反光，背景浅紫雾面渐变。

**主标题**（行楷 / Snell Roundhand，最大字号）：

- 中文：**"看见你没走的那条路"**
- English: **"See the path you haven't taken."**

**副标题**（无衬线 / Times New Roman）：

- 中文："未镜陪你把心里那些想了好久没结论的事，慢慢理一遍。"
- English: "The Other Path walks you slowly through the decisions you've been turning over."

**辅助说明**（更小字号，可选阅读）：

- 中文："不替你做决定，只帮你看清你在选什么。"
- English: "We won't decide for you — we'll help you see what you're choosing."

**CTA**：[下一步] / [Next] · 右上角 [跳过] / [Skip]

---

### 屏 2 · 使用情境承诺

**这屏想做什么**：把 PRD-3 §3.7 的"两种入口"显式告诉用户——你不需要先把自己分类成"理性派 / 反思派"，两种都为你敞开。这是 PRD-2 把"双峰"藏过头之后、PRD-3 显式恢复的灵活性。

**视觉重心**：两个柔焦的入口意象左右并置——左边是分析图表的轮廓（模糊化，不具象数据），右边是一张暗示性的塔罗牌背面 / 镜面。两边以柔光渐变连接，中间留白。

**主标题**：

- 中文：**"反复琢磨，或已经有点倾向——都可以"**
- English: **"Whether you're still turning it over, or already leaning toward something — both are fine."**

**副标题**：

- 中文："未镜有两种入口——直接进入分析，或先抽一张牌作反思的起点。两种都可以，你可以这次试一种，下次试另一种，看哪种适合你当下的状态。"
- English: "The Other Path has two entries — go straight to analysis, or pull a card first as a reflective opening. Both are open. Try one this time, the other next time, whichever fits your state."

**CTA**：[我懂了] / [Got it] · 右上角 [跳过] / [Skip]

---

### 屏 3 · 期待值管理

**这屏想做什么**：承接 PRD-3 §3.5.4"未决定也可以"的承接精神——在用户开始之前，就告诉他"你可以停、可以跳、可以看完还没倾向"。让用户在进入前就被允许，不是走完了才被允许。这一屏是产品 voice 最关键的一屏：决定用户对整个体验的姿态预期。

**视觉重心**：一面静止的水面 / 一道穿过雾的光 / 一杯放在窗边的茶——传达"放下时间压力"。镜面上有缓慢扩散的涟漪（呼应 §11 镜面涟漪加载态）。整体节奏静、慢、留白多。

**主标题**：

- 中文：**"30 分钟，可以慢慢来"**
- English: **"30 minutes. Take your time."**

**副标题**：

- 中文："你可以停，可以跳，可以看完还没倾向。我们不催你出结论——纠结本身在告诉你这件事的赌注真的不小。**未决定本身也是一种状态，不是失败。**"
- English: "Pause at any step, skip what you don't want to fill, finish without leaning toward anything. We won't rush you to a conclusion — the fact you're turning it over tells you the stakes are real. **Not deciding is also a state. Not a failure.**"

**CTA**：[开始你的第一次] / [Start your first session] · 右上角 [跳过] / [Skip]

### 关于英文版翻译质量的诚实标注

英文版三屏文案是**人工翻译版本，不是 native rewrite**（承接 PRD-3 §1.3 + §4.3 双语策略）。翻译追求"达"（意思准确）+ "雅"（不生硬），但不追求完全本土化（不把"未镜"重写成完全不同的英文品牌叙事）。

## §8.5 法律文档配套清单（新增子节）

**章节位置说明**：作为 §8 合规边界的新子节，扩展 §8.4 数据隐私的法律护栏覆盖。

需要在产品上线前完成的法律文档清单：

| 文档 | 内容大纲 | 必要性 | 起草路径 |
|---|---|---|---|
| **ToS** | PRD-3 §8.4.4 已列 7 条核心条款（服务范围、用户责任、不预言性、数据所有权、数据导出 / 删除、数据用途、退款政策） | 必须 | 自行起草 + 法务审核 |
| **Privacy Policy** | 数据收集字段（参 §8.4.1）、用途、保存期、用户权利、第三方数据共享（Stripe / Paddle / 模型 API）、cookie 使用 | 必须 | 法务起草 |
| **Cookie Policy** | 必要 cookie / 功能 cookie（语言切换记忆，参 §12.3）/ 不使用第三方追踪 cookie | 必须 | 自行起草 |
| **未成年人使用边界** | 产品定位 18 岁以上（决策推演涉及职业 / 婚恋 / 生育等成人话题）；注册需勾选"我已年满 18 岁"；ToS 明确未成年人不应使用 | 必须 | ToS 内嵌 |
| **地区合规差异声明** | GDPR（欧盟用户的数据权利、right to be forgotten 实现、DPA）；CCPA（加州用户的 opt-out）；ToS 重申"本服务面向中国大陆境外用户" | 必须（EU + 加州用户实际会有） | 法务起草 |
| **AI 生成内容免责声明** | 推演结果不构成专业建议（法律 / 医疗 / 心理 / 财务）；用户应基于自己的判断做决定 | 必须 | ToS 内嵌（PRD-3 §8.4.4 已部分覆盖、可强化） |
| **退款 / 取消政策** | 单次推演 14 天无条件退款、订阅首月可退、超过期限不退、决策包退款规则（开放点见下） | 必须 | ToS 内嵌（PRD-3 §8.4.4 已列） |

**操作纪律**：每个文档由专业法务审核（不靠自己摸索）。

**→ 开放点（留给 Wenbo / Tech Spec 决策）**：
- 法务审核成本预算（自行起草 + 法务一次性审核 vs 全程法务起草，成本差几倍）；
- 决策包 ¥19.9 的退款规则——3 次未用尽时是否按比例退款？已用 1 次但 30 天内能否退剩余 2 次？这是产品规则不是法律义务，但要在 ToS 写明白；
- GDPR DPA（Data Processing Agreement）的签署对象——模型 API 提供方（DeepSeek / Qwen 等）需要分别签 DPA 还是依赖其平台已有合规框架，这是 Tech Spec 阶段评估。

## §10 多设备策略声明（在 §10 不在 v1 范围内 末尾追加）

**章节位置说明**：作为 §10 已有 cut 列表的延伸，明确多设备策略边界。

PRD-3 §10 已列"Native iOS / Android 应用"为 v1 不做。补充以下多设备策略：

- **v1 只做 Web**——响应式设计，桌面浏览器 + 移动浏览器都支持；
- **mobile-first 设计原则**——核心交互（问卷 / 决策输入 / 推演 / 输出）在移动浏览器上必须 fully usable，桌面浏览器是更大屏幕的优化版本而非"主版本"；
- **不做 PWA**（Progressive Web App）——不增加发版复杂度；
- **不做离线模式**——决策推演必须在线（依赖模型 API）；
- **不做跨设备实时同步**——用户在桌面写一半切手机继续这种场景，靠"保存到思考流"承担（用户登录新设备后看到自己的思考流），不需要实时同步。

理由：v1 资源只够把核心 Web 体验做好，多端策略以"覆盖最广 + 复杂度最低"为优先。

## §11 UI 视觉规范（新增独立顶级节）

**章节位置说明**：与 §5 内容与文案原则平行——§5 管文案纪律，§11 管视觉纪律。两节合在一起构成产品整体表达层的双轨。

### §11.1 视觉哲学（总纲）

**一句话总原则**：

> 整体视觉以浅紫与纯白为基调，通过低饱和雾面渐变与微透光玻璃质感，营造克制、轻盈且带呼吸感的"梦核"氛围；所有视觉细节严格服务于"不替你做决定，只陪你慢慢理清"的产品哲学，让朦胧感成为思考的缓冲，而非阅读的障碍。

视觉哲学服务两件事：
1. **心理安全 + 留白**——避免具象奇幻或压迫感，让正在纠结的用户感觉被允许慢下来；
2. **镜子语言贯穿**——以"镜子"为核心隐喻，统一首页大镜子 + 各子页面的轻量延续（卡片边缘微反光 / 弧面分割线 / 镜面涟漪加载态 / 倒影空白态）。

### §11.2 颜色规范

| 维度 | 规则 |
|---|---|
| 基调 | **浅紫 + 纯白**——浅紫作为情绪色，纯白作为留白与可读性底色 |
| 渐变 | **低饱和雾面渐变**——浅紫 → 极浅紫 → 白；不出现高饱和、高对比的渐变 |
| 质感 | **微透光玻璃**（frosted glass / glassmorphism 的克制版）——卡片、按钮、输入框带轻度毛玻璃质感，不要纯实色块 |
| 强调色 | 极少使用——CTA 按钮可用稍深的紫做点睛，但不出现红 / 黄 / 橙等高警示色 |
| 错误 / 警示色 | 用稍深的灰紫，不用红——保持 voice 一致（错误时刻不破"陪你慢慢理"的氛围） |

**明确不要做的反例**：
- 高饱和紫（接近紫罗兰 / 茄紫）——压迫感；
- 大面积深色背景——失去"轻盈呼吸感"；
- 霓虹效果 / 赛博朋克风——与产品哲学完全冲突；
- 过度毛玻璃（每个元素都模糊）——朦胧感变成阅读障碍。

**→ 开放点（留给 Tech Spec / 设计师产物）**：
- 颜色 token 体系（Primary-Purple / Secondary-Purple / Surface-White / Surface-Mist 等具体色值）；
- 暗色模式是否做 v1（开放点：v1 默认只做亮色，暗色模式作为 v2+ 候选）；
- 各设备色彩校准（移动端 sRGB / 桌面端 P3）。

### §11.3 字体规范

| 用途 | 中文版 | 英文版 |
|---|---|---|
| 品牌标识 + 核心标题 | **思源行楷** | **Snell Roundhand** |
| 正文 + 交互组件 | **现代无衬线**（具体选型留 Tech Spec） | **Times New Roman** |

**字体使用约束**：

- **行楷 / Snell Roundhand 只用于品牌名 + 核心标题**——不用于正文、不用于交互组件、不用于 micro copy。否则失去"东方情绪张力 / 陪伴感"的稀缺性；
- **现代无衬线 / Times New Roman 必须保障可读性**——信息层级清晰、字号最小不低于工程合理值，具体由 Tech Spec 定（建议参考 14px web baseline / 16px mobile baseline）；
- **中英文版不假装"字体同质"**——视觉风格在两种语言里各自成立（承接 PRD-3 §1.3"英文版是人工翻译版本、不是 native rewrite"的诚实化）。

**→ 开放点（留给 Tech Spec）**：
- 中文正文无衬线选型——候选：思源黑体 / OPPO Sans / 苹方（移动端默认）/ 系统字体 fallback 链；
- 字体 fallback 链（特别是中文 web font 加载失败时）；
- Times New Roman 在英文 mobile 浏览器的渲染（小字号下衬线易糊，可能需要切换到 Georgia / Charter 作为 mobile fallback）。

### §11.4 镜子语言的页面级应用

**首页（落地页）核心**：占据视觉重心的大镜子——镜面呈柔焦水波或微折射效果，隐喻"照见未走之路"而非给出答案。镜子里映出的不是具体场景（不具象奇幻），是模糊的远景或抽象路径。

**各子页面的镜子语言延续**（轻量、非干扰）：

| 页面元素 | 镜子语言落地 |
|---|---|
| 卡片 | 边缘微反光（subtle highlight），让卡片像浮在镜面上 |
| 分割线 | 弧面折射感（不是直线，是带轻度弧度的渐变线，呼应水波） |
| 加载态 | **镜面涟漪**（缓慢从中心扩散的同心圆，1-2 次循环为一周期）——不用 spinner / progress bar |
| 空白态 | 留**倒影**（如思考流空时，显示一个浅紫倒影 + 一句话："你的第一次推演会出现在这里") |
| 按钮 hover | 微透光感增强（毛玻璃透明度从 70% → 85%），不是颜色突变 |
| 输入框 focus | 边缘有柔光呼吸效果，像镜面被轻轻擦亮 |

### §11.5 镜子语言与开场镜子模块（§3.3 反思式塔罗）的视觉关系

**→ 开放点（留给 Tech Spec / 设计师 + Wenbo 决策）**：

PRD-4 提出两个候选方向，留待决策：

**方案 A · 同一套视觉语汇**：开场镜子模块（抽塔罗、用户投射、AI 凝练）使用与全产品相同的浅紫雾面 + 镜面涟漪语言。塔罗牌图像作为镜面内浮现的元素出现，不是独立的牌阵 UI。
- 优点：视觉一致性强，整个产品像一面统一的镜子；
- 风险：塔罗的传统视觉（牌面构图、象征图案）可能被弱化到失去"具象触发"的力量——而开场镜子的核心价值之一就是塔罗图像作为高密度 prompt。

**方案 B · 镜子语言是底色，塔罗模块在底色之上做独立视觉**：全产品基调是浅紫雾面 + 镜面涟漪，开场镜子模块时塔罗牌作为"放在镜面上的具象物"出现——保留传统牌面视觉的密度（但用克制的现代化重绘版本），与底色形成柔和层次。
- 优点：塔罗作为反思 prompt 的具象力量保留；
- 风险：两套视觉语汇并存，需要更精细的设计协调。

**PRD-4 倾向 B**——理由：开场镜子的产品价值依赖塔罗图像的"具象触发"（参 §3.3 + §11.5 工程基础），如果统一为镜面雾面会消解这部分价值。但最终方向待 Wenbo / 设计师评估视觉协调成本后定。

### §11.6 动效原则

- **轻柔缓慢**——动效时长建议 300-600ms（不是 100ms 的"快"，是 500ms 的"舒缓"）；
- **节奏舒缓**——多用 ease-in-out 缓动曲线，不用 linear；
- **服务于思考的缓冲**——动效不是装饰，是给用户"喘口气"的视觉时间。例如 Step 之间的过渡用柔光淡入淡出，让用户感受到"上一步结束、下一步开始"的节奏感；
- **不出现**：弹跳（bounce）、抖动（shake）、闪烁（flash）、突然放大（pop-in）等带紧张感的动效。

**→ 开放点（留给 Tech Spec）**：
- 具体的动效曲线 token（cubic-bezier 参数）；
- 动效降级策略（reduced-motion 用户偏好的支持）；
- 加载态镜面涟漪的实现成本评估（CSS 动画 vs Lottie vs Canvas）。

### §11.7 明确不要做的反例

| 反例 | 为什么不做 |
|---|---|
| 具象奇幻（独角兽 / 水晶球 / 神秘仪式场景） | 把产品推向 fortune-telling 标签，与"不预言"纪律冲突 |
| 压迫感（深色基调 + 高对比 + 锐利边缘） | 让正在纠结的用户更焦虑，违反"心理安全"原则 |
| "梦核"被滥用（每个角落都雾蒙蒙） | 朦胧成为阅读障碍，用户找不到可点的按钮 |
| 朦胧变成阅读障碍 | 正文 / 交互组件必须保持高可读性——朦胧感只在装饰层（背景 / 装饰元素） |
| 多种风格混用（极简 + 国潮 + 赛博） | 失去识别度，用户记不住产品 |
| 高饱和强调色（红 / 黄 / 橙 / 荧光绿） | 与浅紫雾面基调冲突，破坏整体氛围 |

### §11.8 服务于产品哲学的总原则（收尾）

整个视觉系统的设计目标：让用户在使用产品的每一秒都感受到"我是被允许慢下来的"。

视觉的"轻、慢、雾、镜"不是审美选择，是产品哲学的视觉化身——产品要陪用户慢慢理一遍纠结，视觉就要给出"慢"的物理感受；产品不替用户做决定、只映照，视觉就要让用户看到自己（而不是看到 AI 在表演）。

如果某个具体设计决定让用户感觉"产品很聪明 / 很厉害 / 很科技"——那是错的方向。

如果让用户感觉"在这里我可以喘口气"——那是对的。

### §11.9 品牌系统 / Logo 视觉需求

**章节位置说明**：作为 §11 视觉规范的子节，处理产品名落地的具体视觉需求。

#### 中文 Logo · 未镜

- **字体**：思源行楷；
- **传递**："未来照见之镜"的双重含义——"未"字带笔锋的悬置感（暗示尚未发生），"镜"字结构端正（暗示映照的稳定）；
- **设计方向**：两字 Logo 应有轻微"墨韵"感，不要做硬边电脑字；可考虑"未"字最后一笔有轻度晕染或留白（呼应 §11.1 视觉哲学的"朦胧"）；
- **辅助元素**：Logo 下方可加一道浅紫弧线（呼应镜面涟漪），但不做必需。

#### 英文 Logo · The Other Path

- **字体**：Snell Roundhand；
- **传递**：反思 / 岔路 / 选择的氛围（呼应 Robert Frost《The Road Not Taken》的隐喻）；
- **设计方向**：定冠词 "The" 与 "Other Path" 之间的间距 / 大小比例需精心处理——"The" 宜小，让重点落在 "Other Path"；可考虑 "Other" 与 "Path" 之间一段轻微连笔（强化书写感）。

#### 双名 Logo 的统一性

- **字形不强求统一**：异名 / 异字体本就是两种语言各自承载产品灵魂的不同侧面（承接 PRD-3 §0 异名战略）；
- **视觉氛围必须同源**：都体现"梦核 / 浅紫 / 镜子"的产品 identity——具体表现为：两个 Logo 都使用相同的浅紫色（同一色 token）、都有书写感字体、都不出现锐利边缘。

#### 落地页的"未"字纪律应用

承接 PRD-3 §0 + §4.2.1 + §9.15 的"未字纪律"：

> 落地页 Hero 区域显示 Logo 之后，必须紧邻"未镜不是预言之镜"声明文案——不是放在页脚或 FAQ 折叠里，是在用户第一眼看到 Logo 之后立刻看到的位置。

声明文案视觉要求：字号小于副标题（不抢戏），但字色不能淡到看不清（必须被读到）。

**→ 开放点（留给 Tech Spec / 设计师产物）**：
- 详细 Logo 设计稿（PRD 只定方向，不出图稿）；
- Logo 在不同尺寸下的可读性（最小尺寸 / favicon 适配 / app 图标如未来出 native app）；
- 品牌色板的具体 hex 值；
- 中文 Logo 在简繁字形上的处理（未镜 vs 未鏡 — 默认简体，繁体地区是否做适配作为开放点）。

## §12 国际化策略（新增独立顶级节）

**章节位置说明**：与 §4 信息架构与交互流程平行——§4 管页面层级，§12 管语言层级。

### §12.1 默认语言判定（C 方案）

按浏览器 `Accept-Language` header 自动判定：

- `zh-*`（包括 zh-CN, zh-TW, zh-HK, zh-SG）→ 中文版；
- 其他 → 英文版；
- 无法判定（缺失 header / 异常值）→ fallback 到英文版。

### §12.2 用户切换路径

- 右上角始终显示语言切换按钮（中 / EN）；
- 用户点击即时切换，不弹拦截弹窗；
- 切换不丢失当前页面状态（如正在填问卷的内容、思考流卡片）。

### §12.3 切换后状态保留

- 用户的切换选择保存在 `localStorage`（键名：`mirror.lang`）；
- 下次访问时**优先使用用户保存的选择**（覆盖浏览器自动判定）；
- 如果用户清除浏览器数据，回到浏览器自动判定逻辑；
- 登录用户的语言偏好同时同步到账号 profile（跨设备一致）。

### §12.4 文案等价性

- 中英文版的产品文案在两种语言中**完全等价**——都磨过 voice、不存在"英文是阉割版"或"英文功能少"；
- 但承接 PRD-3 §1.3 的诚实：英文是人工翻译版本、不是 native rewrite；
- 翻译腔与文化色彩残留（如"探索者的远行"→"The Explorer's Journey" 的 self-help 色彩）是已接受的 trade-off。

### §12.5 不做的事

- **不强制按 IP 判定**——可能错判 VPN 用户（大陆境内 VPN 用户的 IP 显示为美国 / 日本等，但他们读中文）；
- **不弹"是否切换语言"的拦截弹窗**——破坏 onboarding 滚动条 / 用户体验；
- **不把"语言切换"埋在 menu 深处**——必须右上角始终可见。

### §12.6 第三种语言扩展边界

- v1 只做中英；
- 其他语言（日 / 韩 / 西 / 法 ……）作为 v6+ 候选；
- v1 不预留多语言架构（避免过早抽象）——但 i18n 字段命名规范要从一开始就规范化（Tech Spec 定）。

## §13 错误处理与降级的用户面体验（新增独立顶级节）

**章节位置说明**：作为新顶级节，与 §3 核心功能模块的"异常路径"（§4.3）配套——§4.3 列产品级异常路径，§13 管错误时刻的 voice 纪律。

### §13.1 错误场景表格

| 错误场景 | 用户面表现 | 文案 voice 要求 |
|---|---|---|
| AI 调用超时 | 等待动画 + 30 秒后温柔提示 | "我这边再想一下——网络好像有点慢，要不要稍等几秒？如果超过 1 分钟还没出来，你可以刷新或者明天再试。" |
| AI 调用失败 | fallback + 用户可重试或保留输入 | "今天我这边不太顺手，你刚才写的内容已经存好了，要不要明天再来一次？" |
| 双层一致性审查 fail（原型层和结构层冲突） | 重写最多 2 次，仍 fail 则跳过原型层只给结构层 | "这个推演的'故事核'部分今天没有顺利做出来——我先把结构化分析给你。故事核如果你想要，可以让我重新尝试。" |
| 模型返回违反纪律内容（出现禁用词）被关键词过滤拦截 | 重写最多 2 次，仍违反则给安全 fallback + 内部 log | "这一段我没说清楚，让我重新组织一下。"（若仍失败：回到上一步让用户选择跳过或 retry） |
| 网络断开 | 用户输入本地缓存、网络恢复后自动重试 | "好像断网了——你刚才填的没有丢，网络回来我们继续。" |
| 用户操作过快 / 后端限流 | 软性拦截 | "我跟不上了——慢一点，我们一起想。"（契合产品 voice "慢慢理"） |
| Step 4 用户尝试跳过必填 | 软性提示，不报错 | "这一步我陪你想——你的直觉这件事只有你自己知道，我帮你看清它里面藏着什么。慢慢说，我等你。" |
| 用户输入超长（如决策描述 > 5000 字） | 软性提示截断，不报错 | "你写得很多——为了让我能好好理一遍，先帮你保留最近的 X 字，全文我也存了，等会可以回看。" |
| 支付失败 | 保存推演进度、提示重试 / 换支付方式 | "支付那边没走通——你的推演已经保存好了，等支付回来我们继续。要试试别的支付方式吗？" |

### §13.2 硬性要求

- **所有错误文案禁用技术语言**——不出现 "500 Server Error" / "Network Error" / "请求失败" / "API 异常" / "Token Limit Exceeded" 等；
- **用户面文案保持"陪你慢慢理一遍"的 voice**——错误时刻是 voice 最容易破功的地方、最需要纪律。一句"系统繁忙请稍后重试"会让 voice 全面崩塌；
- **不暴露技术细节**给用户——API 名 / 模型名（DeepSeek / Qwen 等）/ token 数 / queue 位置等都不显示；
- **用户的所有输入必须本地缓存**——问卷答复、决策描述、Step 4 概率档位、Pre-mortem 文本、开场镜子的用户投射，在错误发生时都不能丢；
- **错误时给用户一个明确的下一步**——不要只说"出错了"，要说"出错了，你可以 X 或 Y"；
- **错误日志内部记录**——便于产品改进，但不暴露给用户。

### §13.3 错误时刻的 fallback 优先级

当多重错误同时发生时（如：模型超时 + 网络中断 + 用户输入很多），fallback 的优先级：

1. **保住用户输入**（最高优先级）——本地缓存 + 用户可见"你的内容已保存"；
2. **保住产品 voice**——文案不破功；
3. **保住可用性**——给用户一个可执行的下一步（重试 / 跳过 / 明天再来）；
4. **失败时的优雅退场**——如果以上都不可能，至少给一个"今天先到这里，明天我再陪你想"的温柔结尾，不留刺耳的错误页。

### §13.4 → 开放点（留给 Tech Spec）

- 各错误场景的具体重试策略（次数 / 间隔 / backoff）；
- 本地缓存的实现（localStorage vs IndexedDB vs sessionStorage）；
- 错误日志的内部记录格式 + 隐私保护（不记录用户的决策内容明文，只记录元数据）；
- 模型 API 多通道 fallback（主模型失败时切备用模型，承接 PRD-3 §10.1"一家为主一家为备"）。

## §14 客户支持 / 用户反馈渠道（新增独立顶级节）

**章节位置说明**：作为新顶级节，与 §6 评估指标体系并列——§6 管系统性指标，§14 管个体反馈渠道。两者一起构成产品改进的双轨。

### §14.1 入口 1 · 反馈表单（主入口）

**位置**：产品内顶部 / footer 持续可见的"反馈"按钮（每个登录页面都有）。

**表单字段**：

| 字段 | 必填 | 说明 |
|---|---|---|
| 反馈类型 | 必填 | bug / feature request / 内容反馈 / 其他 |
| 详细描述 | 必填 | 自由文本 |
| 可选邮箱 | 选填 | 留邮箱可获回复（不留也可提交） |
| 是否允许联系 | 选填 | 默认勾选，用户可去掉（GDPR 友好） |

**提交去向**：Wenbo 邮箱 + 后台系统。

**响应承诺**：不承诺 SLA（indie 资源不允许），但 ToS 明确"我们读每一条、有意义的反馈会回复"。

### §14.2 入口 2 · 一键反馈（轻入口）

**位置**：

- 推演完成页（每次推演结束）；
- 关键交互后（如开场镜子凝练确认后、Step 5 偏差审计点[我不同意]后）。

**形式**：一行问句 + 三个 emoji 按钮 ☺️ 😐 ☹️

**文案**：

- 中文："今天用得舒服吗？"
- 英文：以"How was it?"

**提交去向**：产品后台 + 关联到该次推演的元数据（用户 ID / 推演 ID / 时点 / 触发场景）。

**用途**：

- 作为产品改进的高频信号源；
- 不进入 NPS 计算（NPS 用决策回访 + 50 用户深访的专项数据）；
- 高频出现 ☹️ 的场景进入 backlog 优先级。

### §14.3 反馈数据的产品改进闭环

- **每周自动汇总**（初期可手工，规模上来后做后台 dashboard）——Wenbo 自己看；
- **高频抱怨进入 backlog**——按 issue 频次 + 影响范围排序；
- **触及 idea 锁定后的硬约束的反馈**（Barnum 护栏 / 不预言 / 双层一致性 / 主语永远是用户）**不能让 agent teams 自决修改**——必须 Wenbo 决策（详见即将写的 CLAUDE.md）；
- **触及 PRD 锁定纪律的反馈**（如禁用词清单 / Step 4 必填 / 镜子层主语规则）同样需要 Wenbo 审核。

### §14.4 → 开放点（留给 Tech Spec）

- 反馈表单的具体技术实现（自建 vs 接入 Tally / Typeform 等第三方）；
- 邮件接收方案（Wenbo 个人邮箱 vs 团队邮箱别名 vs 工单系统）；
- 一键反馈的高频抱怨自动 alert 触发条件（如同一场景 ☹️ 占比 > 30% 时自动推送给 Wenbo）。
