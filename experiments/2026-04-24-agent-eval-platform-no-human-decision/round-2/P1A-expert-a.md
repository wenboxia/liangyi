专家 A 方案 · 通用评测框架派
一、产品定位与目标用户
产品定位
一个与具体 Agent 业务解耦的通用评测中台。核心主张：Agent 输出质量可以抽象为一组跨场景通用的质量维度，通过标准化的评测框架 + 可插拔的场景适配层，实现"一次建设、处处可用"。

平台不为某一类 Agent（客服、代码、搜索、RAG）单独造轮子，而是提供一套评测原语（primitives） —— 维度定义、打分协议、评分器接口、报告 schema —— 让任何 Agent 都能以一致的方式被评测、被比较、被迭代。

目标用户
核心用户（P0）：AI 产品经理、Agent 研发工程师——需要在迭代中判断"这次改动到底变好了还是变差了"。
次级用户（P1）：算法/Prompt 工程师——需要在多个 Prompt 版本 / 模型之间做 A/B。
延伸用户（P2）：业务负责人、QA——需要看整体质量趋势与回归报告。
二、核心评分机制
2.1 通用质量维度（Universal Rubric）
抽取 Agent 输出的五个跨场景通用维度，作为框架的"骨架"。任何 Agent 接入时，这五项默认开启：

维度	含义	典型失败模式
正确性 (Correctness)	输出在事实、逻辑、计算上是否正确	幻觉、事实错误、推理跳步
指令遵循 (Instruction Following)	是否完成了用户/系统指令要求的任务与约束	遗漏要求、越权、格式不符
相关性 (Relevance)	输出是否聚焦于输入真正的诉求	答非所问、冗余、跑题
完整性 (Completeness)	是否覆盖了任务所需的全部要点	少关键步骤、只答一半
表达质量 (Presentation)	结构、语言、格式、可读性	冗长、结构混乱、风格不一致
这五个维度构成通用基座。任何场景都可以在此之上挂载自定义维度（如"安全性"、"引用准确性"、"代码可执行性"），但不能动基座——这是框架可迁移性的保证。

2.2 打分方式：三层打分器（Scorer Stack）
每个维度允许使用一个或多个 Scorer 组合打分，平台内置三类：

Rule-based Scorer：正则、JSON schema 校验、长度、关键词命中等——用于格式、结构、硬约束。
Model-based Scorer（LLM-as-Judge）：用一个裁判模型按标准化 rubric 打分，返回 0–5 分 + 扣分理由。默认使用 CoT + 结构化输出 + 固定 few-shot 锚点 来降低方差。
Reference-based Scorer：当存在 golden answer 时，计算语义相似度 / 精确匹配 / ROUGE 等。
每个维度的最终分 = 该维度下启用的 scorer 的加权平均，权重由场景配置指定，默认等权。

2.3 评分输出协议
每次评测返回一份标准化 JSON 报告：


{
  "overall_score": 3.8,
  "dimensions": [
    {
      "name": "correctness",
      "score": 3,
      "scorer": "llm-judge-v1",
      "deductions": [
        {"reason": "第二段关于 X 的说法与输入中给定的事实冲突", "severity": "major"}
      ],
      "evidence_spans": [[120, 186]]
    }
  ],
  "meta": {"agent_id": "...", "version": "...", "trace_id": "..."}
}
关键设计：扣分必须指向证据片段（evidence span），而不是笼统的"写得不好"。这是从"感觉"走向"量化"的最小硬要求。

2.4 打分一致性保障
Rubric 校准集：每个维度维护 20–50 条人工标注样本，作为 LLM-judge 的校准锚点，并周期性跑 Judge-vs-Human 一致性（目标 Cohen's κ ≥ 0.6）。
Judge 漂移监控：模型升级或 Prompt 变更时，自动在校准集上回放，超过阈值报警。
多裁判投票（可选）：关键场景支持 N 个 judge 投票取中位数，降低单模型偏差。

关键架构原则：

Scorer 是插件：统一接口 score(input, output, context) -> DimensionScore，新增 scorer 不动内核。
Rubric 即配置：维度定义、权重、prompt 模板、few-shot 全部以 YAML/JSON 声明，可版本化、可 diff、可回滚。
Run 不可变：每次评测留 trace_id，输入、输出、judge prompt、judge 原始响应全量存档，任何分数都能追溯复现。
场景通过 Profile 接入：一个 Profile = 一组维度选择 + 权重 + scorer 配置 + 可选数据集。接入新 Agent = 选/写一个 Profile，不改代码。
四、冷启动与采纳路径
评测平台最大的死法不是技术——是没人用。采纳路径分三阶段：

Phase 1：单点引爆（0–4 周）
选团队内一个痛点最强的 Agent（通常是对外的、迭代频繁的），不做平台化，先手工把通用 rubric 跑通。
交付物：该 Agent 每周自动出一份质量报告，上到周会。让一个 PM 第一次用数据而不是"感觉"讨论质量——这是最强采纳杠杆。
Phase 2：粘贴即用（4–10 周）
上线 Web UI 的"粘贴输入+输出 → 一键评分"最小闭环，默认使用通用 rubric，无需配置。
关键体验指标：从粘贴到拿到报告 < 30 秒，报告每一条扣分都能点到证据。
此阶段目标是让更多 PM/工程师自发使用，靠单次体验驱动留存。
Phase 3：框架化沉淀（10 周+）
推动各业务线把自己的 Agent 以 Profile 形式接入，批量回归、版本对比、CI 集成。
建立校准集治理机制和维度扩展评审：新增自定义维度需提交校准样本 + 一致性数据，保证框架不被私货稀释。
采纳设计原则
先给结论，再给配置：默认就有可用的通用 rubric，不逼用户先设计维度。
对比优先于绝对分：产品内最显眼的永远是"本次 vs 上次"的 diff，而不是一个孤立的 3.8 分。
扣分可反驳：每条扣分都可以一键标"不同意"，反馈回流到校准集——让用户参与改进框架，而不是被框架审判。
五、关键风险与对策
风险	影响	对策
LLM-judge 不稳定 / 有偏	分数不可信，用户失去信任	校准集 + 一致性监控 + 固定 few-shot + 多裁判投票；关键维度强制要求 rule-based 兜底
通用维度在具体场景"不够用"	被质疑"太泛、抓不住重点"	通用维度作为基座不可删，但允许场景扩展自定义维度；靠 Profile 机制保证灵活度
Judge 成本失控	大规模回归时 API 费用爆炸	LLM Gateway 层做缓存（相同 input+output+rubric 命中缓存）、异步批处理、小模型预筛 + 大模型复核的级联
"评分数字化"带来假安心	大家只看总分，忽略分布与长尾	报告默认展示分布 + 最差样本 Top N，而不是只有均值；产品引导用户看 bad cases
用户觉得"粘贴太麻烦"	采纳停在 Phase 2	提供 SDK / OpenAI-compatible proxy / 日志接入三种路径，让评测可以被嵌入而不是被访问
框架被私有维度稀释成"一堆脚本"	退化成任务特定工具，失去通用性	维度注册需走评审；校准数据、一致性指标作为硬门槛；定期审计 Profile 复用率
一句话主张：Agent 质量评测的终局不是"为每个 Agent 各写一套评测"，而是建立一套维度标准化、打分可追溯、场景可插拔的通用框架——让质量讨论从"我觉得"变成"这条扣分的证据在第 120–186 字符"。
