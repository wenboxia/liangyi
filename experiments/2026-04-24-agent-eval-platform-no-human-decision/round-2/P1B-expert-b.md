# 专家 B 方案 · 任务定制化评测派

## 一、产品定位与目标用户

### 1. 产品定位
**一个贴着业务场景走的 Agent 任务级诊断平台**，而非通用排行榜。

平台的核心预设是：不存在一套放之四海皆准的 Agent 评测指标。每一个 Agent 输出质量的好坏，必须在其所服务的具体业务任务、上下文规则、交付标准下定义。评测的真正价值不是产出分数，而是产出**“下一步该改什么”的明确指令**——对工程师是具体到 prompt、工具选择、检索策略的调整方向，对产品经理是业务规则是否需要收紧、边界 case 是否要补的决策信息。

### 2. 目标用户
- **Agent 产品经理（主用户）**：他们需要用业务语言定义“好输出”的标准，看到扣分原因，判断 Agent 是否可上线或需要回滚。
- **Agent 工程师 / 提示词工程师（核心执行用户）**：他们需要明确的优化线索，例如“在第3轮指代消解失败”、“领域知识引用陈旧”、“输出格式偏离模板规范”。
- **领域专家 / 业务审核人（间接用户）**：参与评测标准校准，平台通过他们的少量标注来锚定“业务真相”。

## 二、核心评分机制：任务定制化评分卡

### 1. 维度体系：从“任务画像”动态生成评分维度
平台不预设固定的通用维度（如流畅度、相关性），而是要求用户首先定义**任务画像**。任务画像由三要素构成：

- **任务类型**：对话、文档生成、结构化抽取、多步推理、代码合成、分类/意图路由等。
- **业务场景模版**：客服、营销文案、合同审查、医疗问诊摘要、内部知识库问答等。每个场景模版预置一套可裁剪的维度库与业务规则示例。
- **交付规范**：输出格式要求（JSON schema、Markdown 结构、特定字段必填/禁止）、风格约束、合规红线列表。

系统根据任务画像，自动推荐一组 **“评分卡维度”** ，用户可增删、调权、设定每个维度的具体判罚条件。典型维度示例（针对“电商客服 Agent”）：

| 维度 | 定义（可业务化配置） | 评分方式 |
|------|---------------------|----------|
| 业务解答准确性 | 是否命中知识库标准话术、是否错误承诺、是否违反售后政策 | 关键点对点判分 + 红线一票否决 |
| 多轮对话指代与状态追踪 | 是否正确解析用户所指的商品、订单号、上一轮未解决问题 | 指代链检测 + 状态比对 |
| 服务语气与品牌合规 | 是否使用禁用词、是否有情绪对抗、是否符合品牌调性 | 规则 + 判别模型 |
| 输出格式遵从 | 是否严格遵循预设的响应模板（开头问候、分点呈现、结尾确认等） | 结构解析 + 模板匹配 |
| 信息充分性 | 是否遗漏用户场景中必须反问的关键信息（如尺寸、地址、退换原因） | 必问项清单检查 |
| 结单/转人工判断 | 是否在不应结单时强行结束会话，或在不满足转人工条件时转交 | 状态机规则 |

每个维度不产生模糊的“1–5分”，而是产生**结构化扣分项**：
- **扣分项**：具体描述“哪里出了问题”，附原始输出片段。
- **严重级别**：红线/严重/轻微。
- **修复建议**：对于代码/配置层面的问题，给出可操作的提示（例如“建议在 prompt 的 few-shot 中增加携带订单号的变体示例”、“开放检索到的运单状态字段使用错误”）。

### 2. 打分方式：规则引擎 + LLM-as-a-judge 证据链
我们坚决反对直接让 LLM 给一个总分。打分流程强制分层：

1. **规则层（硬约束）**：预定义的格式模板、关键词黑白名单、JSON 有效性、必填字段存在性等。不通过直接触发红线扣分，无需进入语义层。
2. **业务知识校验层**：将业务规则（如“电子产品退货必须是7天内”）结构化为一组断言，每条断言基于输出文本和上下文自动验证。
3. **LLM 证据提取层**：对复杂语义维度（如语气、逻辑冲突），调用 LLM 不做评分，只做**证据抽取**：“输出文本的哪个片段支持/违反了该维度的什么条件”。抽取结果形成证据片段集合。
4. **评分聚合**：由确定性逻辑根据证据和规则计算维度得分，并生成扣分说明。绝不把最终判定权交由黑盒模型。

分数呈现上，平台不强调总分，而是强调**各维度健康度**和**红线触发清单**。可以有综合等级（例如“可上线 / 需修复 / 不可上线”），但该等级由业务侧配置的维度和红线组合决定，不是加权平均。

## 三、系统架构要点

### 1. 评测任务生命周期
- **任务定义层**：用户粘贴或导入一组 Agent 的输入（上下文、用户消息）和输出（可批量 CSV/JSON），选择或新建任务画像，生成评测配置。
- **执行引擎**：并行执行规则层 → 业务校验层 → LLM 证据抽取层。LLM 调用限定在证据抽取，使用自部署或可控模型，并强制输出结构化 JSON 便于解析。
- **报告生成层**：生成交互式 HTML 报告，可下钻到每个 case 的每条扣分项及其原文定位，支持分享链接和权限控制。

### 2. 任务配置与知识注入
- **场景库（Scenario Store）**：提供按行业和任务类型预制的维度、规则断言模板、业务知识 schema。用户可以 fork 场景模板进行私有化扩展。
- **业务知识接入**：支持同步知识库、FAQ 库、政策文档到评测环境，使业务校验层能针对最新业务知识进行验证。也支持上传“黄金参考输出”或标准操作流程（SOP）作为评估参考系。
- **自定义函数钩子**：对于特殊校验逻辑（例如需要调用订单系统验证状态），允许用户编写轻量级校验函数（Python/JS）或配置 API 调用，作为规则层的一部分。

### 3. 评测数据管理与闭环
- **评测集版本化**：每次评测任务与输入集、配置快照绑定，可复现对比。
- **人工校验与反馈闭环**：用户可以对自动抽取的证据和扣分进行“有用/误判”标记。标记数据自动回流，用于调整证据抽取 prompt 的 few-shot 示例，并微调小模型（若部署），逐步降低误判率。
- **回归评测触发**：支持 CI/CD 集成，当 Agent prompt 或工具配置变更时，自动触发指定评测集并对比上一版本各维度变化，生成差异报告。

### 4. 可扩展性
- 插件式维度：新维度以配置文件或代码插件形式热加载。
- 评测面板可嵌入内部 Agent 平台，通过 API 提交评测，获取报告链接。

## 四、冷启动与采纳路径

### 1. 冷启动策略：用“诊断工作坊”代替“空平台”
直接在团队内推广一个空白评测平台会遭遇巨大阻抗——用户缺乏动力去抽象任务画像。我们的路径是：

- **“带病评测”导入**：挑选团队当前争议最大的 10–20 条 Agent 输出，由领域专家和我方（专家角色）一起，在 1–2 小时内进行结构化回顾，当场提炼出属于该团队的任务画像、核心维度和 20+ 条具体判例。将这个过程固化为平台内的第一个“任务配置包”。这种即时可见的商业价值是：原本说不清的“感觉问题”，变成了可列举的具体缺陷清单。
- **预置高价值场景包**：根据目标行业（如 SaaS 客服、开发者工具 Agent、内容生成）提供 3–5 个开箱即用的场景模板，包含常见产品和工程团队最头疼的维度和规则。确保用户导入数据后 5 分钟内得到一份可读的扣分报告，降低“第一次配置成本”。

### 2. 采纳与扩展路径
- **从案例复盘到常态卡点**：先在 Agent 上线前评审（go/no-go 会议）中使用，让平台成为决策依据。一旦团队习惯看报告做决策，自然会要求在迭代时也使用，形成“改完就跑一遍评测”的习惯。
- **工程师自驱的动力设计**：评测报告直接指出 prompt 或工具调用中的具体问题（如“在这一步 system prompt 没有明确禁止编造退款链接”），让工程师感受到这是“调试器”而非“监督工具”。
- **渐进式打标与自动化提升**：初期可接受半自动化——团队在平台上对少量 case 进行人工评判，平台学习标准后逐步自动扩展。目标是：标签积累到 50–100 条，即可使自动化评分与专家一致性超过 85%，从而大幅减少人工复核成本，形成正向飞轮。

## 五、关键风险与对策

### 风险 1：评测标准本身不稳定，变成“第二套主观感觉”
**表现**：维度定义模糊、LLM 证据抽取不稳定，导致评测结论又在团队内引发新一轮“感觉”争论。

**对策**：
- 维度必须操作化：每个维度必须配置具体的**可判定的检查项**（是/否/不适用），而非抽象概念。平台在维度编辑界面强制要求提交“判据样例”和“反例”。
- 证据溯源不可妥协：任何扣分必须附原文定位，允许一键查看，让人能即时验证合理性。
- 内建评测者评校：对证据抽取 LLM 定期用人工标注的 Golden Set 进行准确性监控，若有漂移则触发 recalibration。

### 风险 2：过度定制导致维护成本爆炸，平台不可规模化
**表现**：每个任务都需要手工打造维度，团队可能无力为每个 Agent 维护一套独立标准。

**对策**：
- 采用“继承—变异”模式：一个场景模板可衍生出针对特定渠道、特定 Agent 版本的变体，变体仅覆写差异部分，维度定义和规则存在层级继承关系，修改父模板可批量传播。
- 提供维度复用度分析，发现多个业务都关心的共性维度（如事实准确性）可沉淀为平台级维度插件，结合业务特定参数使用。
- 内置基于相似任务画像的维度推荐，降低从零定制的发生频率。

### 风险 3：团队抗拒“额外的评测工作”，采纳失败
**表现**：成员认为在正常迭代之外还要维护评测标准、导入数据、查看报告是负担。

**对策**：
- 评测必须无缝嵌入已有工作流：支持 IDE/PR 注释格式导入，支持从日志系统自动拉取样本，支持与 Jira/Linear 任务关联创建“评测任务”。
- 早期强调“节省评审会议时间”：将 1 小时的 case 争吵会议压缩为 10 分钟看报告定行动项。
- 让得益最直接的角色（工程师）最先体验到价值：报告明确指出 prompt 修改建议，被采纳后可一键记录改善对比，形成个人效率提升故事。

### 风险 4：复杂任务中，证据抽取 LLM 本身的偏见与错误
**表现**：在微妙语境（讽刺、行业黑话）中，LLM 证据抽取可能系统性地误判，扣分失实。

**对策**：
- 不确定性量化：LLM 抽取证据时须同时输出置信度，低置信度项自动标记为“需人工复核”，并悬停显示模型的推理理由。
- 人机协作的“争议”机制：允许用户对任一扣分提出争议，争议案例自动进入样本审查池，用于定期提升模型。
- 对高风险领域，支持退化为纯规则+关键词+人工，不让 LLM 介入红线判定，严守安全边界。
