# Agent 评测平台(v1)

## 一、产品定位与目标用户

### 1.1 产品定位

**一个以"可追溯证据"为核心、以"任务画像"为组织方式的 Agent 质量诊断平台**。

平台的根本主张是:Agent 质量评测既不能退化成"为每个 Agent 手写一套脚本"的碎片化工具,也不能虚化成"一套放之四海而皆准的五维打分"。真正可用的评测系统,必须同时满足两件事:

- **骨架统一**:存在一层跨场景通用的评测原语(维度定义、打分协议、证据 schema、报告结构),保证不同 Agent 可以被一致地评测、比较、回归。
- **血肉贴身**:每一次具体评测都绑定到一个"任务画像",由业务规则、交付规范、红线清单填充通用骨架,使评分结果能够直接指向"下一步改什么"。

平台不追求产出一个漂亮的总分,而是追求产出**一份带证据定位的、可反驳的、可复现的扣分清单**——让团队的质量讨论从"我觉得 3 分有点低"变成"第 120–186 字符的这句话违反了退货政策规则 R-07"。

### 1.2 目标用户

| 优先级 | 角色 | 核心诉求 |
|---|---|---|
| P0 | AI 产品经理 | 用业务语言定义"好输出",在上线/回滚决策中用数据而非感觉 |
| P0 | Agent / Prompt 工程师 | 拿到指向具体 prompt、工具、检索策略的优化线索,在迭代中判断改动是正向还是负向 |
| P1 | 算法工程师 | 在多个 Prompt 版本 / 模型之间做 A/B 与回归 |
| P2 | 领域专家 / 业务审核 | 贡献少量高质量标注,锚定"业务真相";参与校准集治理 |
| P2 | 业务负责人 / QA | 查看整体质量趋势、长尾分布、回归报告 |

## 二、核心评分机制

### 2.1 两层维度体系:通用基座 + 任务画像

平台在维度设计上采用"通用骨架 + 场景血肉"的两层结构,这是本方案最核心的折中。

**第一层:通用基座维度(Universal Rubric)**

任何 Agent 接入时默认开启的五个跨场景通用维度,构成评测框架的骨架,**不可删除、不可改名**——这是跨 Agent 可比性和框架可迁移性的保证。

| 维度 | 含义 | 典型失败模式 |
|---|---|---|
| 正确性 (Correctness) | 输出在事实、逻辑、计算上是否正确 | 幻觉、事实错误、推理跳步 |
| 指令遵循 (Instruction Following) | 是否完成用户/系统指令要求的任务与约束 | 遗漏要求、越权、格式不符 |
| 相关性 (Relevance) | 是否聚焦于输入真正的诉求 | 答非所问、冗余、跑题 |
| 完整性 (Completeness) | 是否覆盖任务所需的全部要点 | 少关键步骤、只答一半 |
| 表达质量 (Presentation) | 结构、语言、格式、可读性 | 冗长、结构混乱、风格不一致 |

**第二层:任务画像驱动的场景维度(Scenario Rubric)**

接入任意 Agent 前,用户必须定义该 Agent 的"任务画像",由三要素构成:

- **任务类型**:对话 / 文档生成 / 结构化抽取 / 多步推理 / 代码合成 / 分类路由等
- **业务场景**:客服、营销文案、合同审查、知识库问答、医疗摘要等
- **交付规范**:输出格式(JSON Schema / Markdown 结构 / 必填字段)、风格约束、合规红线清单

系统根据任务画像自动推荐一组场景维度,用户可增删、调权、细化判罚条件。以"电商客服 Agent"为例:

| 场景维度 | 判罚条件 |
|---|---|
| 业务解答准确性 | 命中知识库话术、未错误承诺、未违反售后政策 |
| 多轮指代与状态追踪 | 正确解析商品、订单号、上一轮未结问题 |
| 服务语气与品牌合规 | 无禁用词、无情绪对抗、符合品牌调性 |
| 输出格式遵从 | 严格遵循响应模板(问候—分点—确认) |
| 信息充分性 | 不遗漏必问项(尺寸、地址、退换原因) |
| 结单/转人工判断 | 结束/转交时机符合状态机规则 |

**两层的关系**:通用维度保证"可跨 Agent 比较",场景维度保证"可指导具体优化"。每条扣分项必须归属到其中一个维度,不能悬空。新增一个场景维度,必须提交判据样例 + 反例 + 至少 20 条校准样本才能入库,防止框架被"私货"稀释成脚本堆。

### 2.2 打分方式:分层打分器 + 证据链

**核心原则:绝不把最终判定权交给单一黑盒模型。打分流程强制分层。**

**Layer 1 · 规则层(硬约束)**
正则、JSON Schema、长度、关键词黑白名单、必填字段存在性、输出模板结构匹配。违反直接触发红线或固定扣分,无需进入下一层。

**Layer 2 · 业务知识校验层**
将业务规则结构化为断言集(例如"电子产品退货必须 7 天内"、"未验证订单号不得承诺退款"),基于输出文本 + 上下文自动验证。支持自定义函数钩子(Python/JS)或 API 调用,可接入订单系统、知识库、SOP 文档做真实数据比对。

**Layer 3 · LLM 证据抽取层**
针对语气、逻辑冲突、语义完整性等确定性难以穷举的维度,调用 LLM——但 LLM **只抽取证据,不给分**:"输出中的哪个片段支持/违反了该维度的哪一条判据"。抽取结果必须为结构化 JSON,包含 `evidence_span`(字符区间)、`judged_criterion`(命中的判据)、`confidence`(置信度)。

**Layer 4 · Reference 层(可选)**
存在黄金输出时,叠加语义相似度 / 精确匹配 / ROUGE 等。

**评分聚合**
由确定性逻辑根据规则命中、断言结果、证据片段计算每个维度的分数与扣分项列表。聚合规则在 Profile 里显式声明,不是加权平均一个总分。

### 2.3 分数呈现:结构化扣分 + 健康度 + 可反驳

平台不强调"加权总分",强调三件东西:

1. **各维度健康度**(绿/黄/红),由维度下的扣分严重级别和红线触发情况决定
2. **红线触发清单**,任一红线触发即导致综合结论为"不可上线"
3. **综合结论等级**:`可上线 / 需修复 / 不可上线`——由业务侧配置的维度和红线组合决定,不是加权平均

### 2.4 标准化评分输出协议

每次评测返回一份不可变的标准化 JSON 报告:

```json
{
  "verdict": "需修复",
  "dimensions": [
    {
      "name": "业务解答准确性",
      "layer": "scenario",
      "health": "red",
      "deductions": [
        {
          "reason": "未验证订单号即承诺全额退款,违反规则 R-07",
          "severity": "redline",
          "evidence_span": [120, 186],
          "matched_criterion": "R-07:退款承诺必须在验证订单号之后",
          "scorer": "assertion-engine",
          "confidence": 1.0,
          "suggested_fix": "在 system prompt 中增加'退款承诺前必须调用 verify_order 工具'的显式约束"
        }
      ]
    }
  ],
  "redlines_triggered": ["R-07"],
  "meta": {
    "agent_id": "...", "agent_version": "...",
    "profile_id": "...", "profile_version": "...",
    "trace_id": "...", "run_id": "..."
  }
}
```

**两条硬要求**:
- 每条扣分必须携带 `evidence_span`,指向原文字符区间,可在 UI 一键高亮
- 每条扣分必须携带 `matched_criterion`,指向一条具体的判据/规则/断言,而不是笼统的"写得不好"

这是从"感觉"走向"量化"的最小门槛。

### 2.5 一致性与可信度保障

- **校准集(Golden Set)**:每个维度维护 20–50 条人工标注样本,作为证据抽取 LLM 的校准锚点
- **Judge-vs-Human 一致性监控**:周期性回放校准集,目标 Cohen's κ ≥ 0.6;模型升级或 Prompt 变更触发自动回放,超阈值报警
- **置信度与复核**:LLM 证据抽取必须输出置信度,低置信度项自动标记"需人工复核"并显示模型推理过程
- **争议闭环**:用户可对任一扣分一键标记"不同意",争议进入样本池,定期用于 few-shot 调整或小模型微调
- **红线不让 LLM 判**:高风险维度(合规、安全、政策违反)强制走规则层 + 断言层,LLM 只做辅助证据提示

### 3.1 核心架构原则

- **打分器是插件**:统一接口 `score(input, output, context) -> DimensionResult`,新增打分器不动内核
- **Rubric 即配置**:维度定义、权重、判据、断言、prompt 模板、few-shot 全部以 YAML/JSON 声明,可版本化、可 diff、可回滚
- **Run 不可变**:每次评测归档 trace_id,全量存储输入、输出、judge prompt、judge 原始响应,任何分数都能追溯复现
- **场景通过 Profile 接入**:`Profile = 通用维度选择 + 场景维度 + 权重 + 断言集 + 红线 + 数据集引用`,接入新 Agent = 选/写一个 Profile,不改代码
- **场景模板支持继承—变异**:父模板沉淀共性,子变体仅覆写差异部分,避免每个 Agent 从零定制

### 3.2 业务知识注入

- **知识库同步**:FAQ、政策文档、SOP 定期同步到评测环境,供断言引擎引用
- **黄金样本上传**:可上传标准输出或 SOP 作为参考系
- **API 钩子**:断言可调用外部系统(订单、CRM、工单)做真实数据校验
- **自定义函数**:允许写轻量级 Python/JS 校验函数注册为断言

### 3.3 成本与性能控制

- **LLM Gateway 缓存**:相同 input + output + rubric 命中缓存
- **级联调用**:小模型预筛 → 大模型复核关键分歧
- **异步批处理**:大规模回归走批处理 API
- **预算护栏**:Profile 级别配置单次评测成本上限,超出降级或告警

### 3.4 工作流集成

- **SDK / OpenAI-compatible Proxy / 日志接入**三种路径,让评测可嵌入而非只能被访问
- **CI/CD 集成**:Agent prompt 或工具配置变更时,自动跑指定评测集,生成 vs 上一版本的 diff 报告,挂到 PR
- **工单联动**:支持 Jira / Linear 关联创建"评测任务",扣分可一键转为待修复工单

## 四、冷启动与采纳路径

评测平台最大的死法不是技术问题,是没人用。采纳路径分三阶段,**每阶段都必须带着"第一个真实受益者"往下走**。

### Phase 1 · 诊断工作坊 + 单点引爆(0–4 周)

不做平台化。选团队内痛点最强的一个 Agent(通常是对外的、迭代频繁的、有争议的),在 1–2 小时的**诊断工作坊**中,拉上领域专家和该 Agent 的 PM/工程师,现场做三件事:

1. 对 10–20 条争议最大的真实输出做结构化回顾
2. 当场提炼该 Agent 的任务画像、场景维度、20+ 条具体判据、3–5 条红线
3. 把工作坊产物固化为平台里的第一个 Profile

**交付物**:该 Agent 每周自动出一份质量报告,上周会。让一个 PM 第一次用证据而不是感觉讨论质量——这是最强的采纳杠杆。

### Phase 2 · 粘贴即用 + 预置场景包(4–10 周)

上线 Web UI 的"粘贴输入+输出 → 一键评分"最小闭环。提供 3–5 个预置高价值场景包(SaaS 客服、开发者工具 Agent、内容生成、结构化抽取、知识库问答),保证用户导入数据后 **5 分钟内拿到一份可读的扣分报告**。

**关键体验指标**:
- 粘贴到拿到报告 < 30 秒
- 每条扣分都能点到原文证据
- 默认展示"本次 vs 上次"的 diff,而不是一个孤立的总分
- 默认展示分布 + 最差样本 Top N,避免只看均值

### Phase 3 · 框架化沉淀 + 工作流嵌入(10 周+)

- 推动各业务线以 Profile 接入自己的 Agent,建立批量回归、版本对比、CI 集成
- 引入"评测作为 go/no-go 决策依据"的机制:Agent 上线前必过指定评测集
- 建立场景库治理:新增场景维度走评审,校准数据和一致性指标为硬门槛
- 推动评测进入工程师日常:报告明确指出 prompt 修改建议,被采纳后一键记录改善对比,形成个人效率故事
- 半自动化到自动化飞轮:标注积累到 50–100 条,自动评分与专家一致性目标 ≥ 85%

### 采纳设计的四条铁律

1. **先给结论,再给配置**:默认有可用的通用维度 + 行业场景包,不逼用户先设计维度
2. **对比优先于绝对分**:UI 最显眼位置永远是"本次 vs 上次"的 diff
3. **扣分可反驳**:每条扣分都能一键标"不同意",反馈回流到校准集
4. **定位工具而非监督工具**:对工程师,报告是"调试器";对 PM,报告是"决策依据"——绝不是"给人打分的 KPI"

## 五、关键风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| **LLM 判分不稳定/有偏** | 分数漂移、用户失去信任 | 强制分层架构,LLM 只抽证据不给分;校准集 + κ 监控;红线走规则层;低置信度自动人工复核 |
| **评测标准本身变成"第二套感觉"** | 维度模糊,证据抽取不稳,团队再陷争论 | 维度必须操作化(可判定的检查项 + 判据样例 + 反例);证据溯源强制到字符区间;校准集作为硬门槛 |
| **过度定制导致维护爆炸** | 每个 Agent 都要独立维护标准 | 通用基座不可删保证骨架稳定;场景模板采用继承—变异模式;维度复用度分析沉淀平台级插件;相似画像自动推荐维度 |
| **通用维度在具体场景"抓不住重点"** | 被质疑太泛、太虚 | 场景层维度可自由扩展,Profile 机制保证灵活;场景维度权重可盖过通用维度 |
| **Judge 成本失控** | 大规模回归 API 费用爆炸 | Gateway 缓存 + 级联(小模型预筛)+ 异步批处理 + Profile 级预算护栏 |
| **"数字化"带来假安心** | 只看总分,忽略长尾 | 不强调总分,强调健康度 + 红线清单 + 最差 Top N;默认显示分布 |
| **团队抗拒额外工作** | 认为配置维度是负担 | 诊断工作坊代替空平台;SDK/Proxy/日志三路接入;CI 自动触发;强调"把 1 小时争吵会变成 10 分钟看报告" |
| **框架被"私货"稀释** | 退化成脚本堆,失去通用性 | 新维度入库需评审 + 校准数据 + 一致性指标;定期审计 Profile 复用率 |
| **LLM 在微妙语境系统性误判** | 讽刺、黑话、行业术语误扣 | 置信度量化 + 争议池 + 定期 recalibration;高风险领域强制退化为规则+关键词+人工 |

## 六、一句话主张

Agent 质量评测的终局,既不是"为每个 Agent 各写一套脚本",也不是"用五个通用维度糊住所有场景"——**而是建立一套骨架统一、血肉贴身、证据可追溯、判定可反驳的分层诊断框架:通用基座保证可比性,任务画像保证可操作性,分层打分保证可信性,证据链保证可改进性**。让团队的每一次质量讨论,都能精确落到"第 120–186 字符的这句话违反了第 R-07 号规则,建议在 system prompt 里加一条约束"。
