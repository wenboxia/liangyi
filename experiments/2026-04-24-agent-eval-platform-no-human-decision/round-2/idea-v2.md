# Agent 评测平台(v2)

## 0. v2 相对 v1 的立场转变

v1 把自己写成一个"完备的平台",结果每个承诺都只有形容词没有数字。v2 做三件根本性的立场收缩:

1. **不自建,先做胶水**:MVP 基座选定 **Langfuse**(开源、可自托管、span-level feedback + dataset + eval 已原生支持)。自建范围收缩到三块真正不可替代的能力:**业务断言适配器**、**中文本地化场景包**、**效度验证回路**。其余全部 fork / 插件化。
2. **效度优先于信度**:v1 的核心承诺是"量化",但只证明了内部自洽。v2 把 **Profile 准入的硬门槛**改为"分数-线上指标相关性 Spearman ρ ≥ 0.5"(具体数字按维度区分),κ 只是子指标。一个 Profile 如果和线上指标不相关,不允许用于 go/no-go。
3. **承诺全部落到数字和责任人**:每条闭环流程必须有 owner + SLA,每条指标必须有目标值和测量方法,每条冷启动动作必须有人时预算。没有数字的承诺不写。

## 一、产品定位与目标用户

### 1.1 定位

**一个基于 Langfuse 的业务化评测扩展层**。

核心主张不变:评测的价值不是分数,是"证据定位 + 下一步改什么"。但形态变了——不是从零造平台,而是在 Langfuse 之上加三层胶水:

- **业务断言适配器**:把内部订单 / 工单 / 知识库 API 接入评测流程,做 Langfuse 原生不支持的"真实数据比对"
- **本地化场景包**:中文业务语境下的维度模板、判据示例、红线清单
- **效度验证回路**:把评测分数和线上真实指标(CSAT、复问率、人工改写率)做相关性验证,作为 Profile 准入门槛

Langfuse 已经覆盖的:trace 归档、dataset / run 管理、LLM-as-judge、人工标注、CI 集成、版本 diff、span-level feedback。这些**直接用,不重造**。

### 1.2 目标用户(沿用 v1,无变化)

| 优先级 | 角色 | 核心诉求 |
|---|---|---|
| P0 | AI 产品经理 | 上线/回滚决策中用数据而非感觉 |
| P0 | Agent / Prompt 工程师 | 拿到可操作的优化线索 |
| P1 | 算法工程师 | Prompt/模型 A/B 与回归 |
| P2 | 领域专家 | 贡献标注,参与校准集治理 |
| P2 | 业务负责人 / QA | 看趋势与回归报告 |

## 二、核心评分机制

### 2.1 两层维度体系(保留 v1 结构,收紧落地细节)

**第一层:通用基座维度** —— Correctness / Instruction Following / Relevance / Completeness / Presentation。跨 Agent 可比性的最小保证,不可删不可改名。

**第二层:任务画像驱动的场景维度** —— 用户定义任务画像(任务类型 + 业务场景 + 交付规范),系统推荐场景维度。

### 2.2 分层打分器(保留 v1 四层架构)

Layer 1 规则层 / Layer 2 业务断言层 / Layer 3 LLM 证据抽取层(只抽证据不打分)/ Layer 4 Reference 层。细节见 v1,不赘述。

### 2.3 红线:硬红线 vs 软红线(v2 新增,响应批判 6)

v1 一刀切"红线不让 LLM 判",实操第一周就会被迫破例。v2 显式分两类:

| 类型 | 定义 | 判定路径 | verdict 行为 |
|---|---|---|---|
| **硬红线(Hard Redline)** | 可 100% 断言化或规则化(JSON Schema 违反、禁用词命中、必调用的工具未调用、政策数值条款如"7 天内"、PII 泄漏模式) | 仅 Layer 1 + Layer 2 判定,LLM 不参与 | 触发即 `不可上线`,不可覆盖 |
| **软红线(Soft Redline)** | 语义边界模糊(品牌调性、情绪对抗、隐性承诺、歧视性表述、医疗/金融越界建议) | Layer 3 LLM 抽证据 + 置信度 + 必须人工二审确认 | 触发 LLM 证据但未二审 → verdict 降档为 `需人工复核`,不直接判 `不可上线` |

**硬红线清单和软红线清单在 Profile 里分列。**一个 Profile 的硬红线覆盖率(硬红线条数 / 红线总条数)是审计指标:低于 60% 的 Profile 标记为"弱红线保护",上线决策需额外评审。

### 2.4 证据 span 在多轮/多消息结构下的定义(v2 新增,响应批判 5)

v1 写 `evidence_span: [120, 186]` 假设输出是连续文本,多消息/工具调用下根本定位不了。v2 定义统一的 `EvidenceLocator` schema:

```json
{
  "trace_id": "...",
  "node_path": "messages[3].tool_calls[0].arguments.refund_amount",
  "text_span": [12, 28],
  "node_kind": "tool_call_argument"
}
```

`node_path` 采用 JSONPath 指向 trace 中的具体节点(消息、工具调用、检索片段、思考过程),`text_span` 仅在节点值为字符串时使用。`node_kind` 枚举:`final_message` / `intermediate_message` / `tool_call_argument` / `tool_call_result` / `retrieval_chunk` / `thought`。

UI 渲染时按 `node_kind` 决定高亮样式,不同 kind 的扣分在报告里分组展示。

### 2.5 标准化评分输出协议(调整后)

```json
{
  "verdict": "需修复",
  "verdict_reason": "2 项严重扣分 + 1 项软红线待人审",
  "dimensions": [
    {
      "name": "业务解答准确性",
      "layer": "scenario",
      "health": "red",
      "deductions": [
        {
          "reason": "未验证订单号即承诺全额退款",
          "severity": "redline_hard",
          "evidence": {
            "trace_id": "tr_abc",
            "node_path": "messages[3].content",
            "text_span": [12, 45],
            "node_kind": "final_message"
          },
          "matched_criterion": "R-07",
          "scorer": "assertion-engine",
          "confidence": 1.0
        }
      ]
    }
  ],
  "redlines_triggered": {"hard": ["R-07"], "soft_pending_review": []},
  "meta": {"profile_id": "...", "profile_version": "...", "run_id": "..."}
}
```

**v2 删除 `suggested_fix` 字段**(响应批判 5)。v1 把它作为核心亮点,但:
- 没有"应用建议→复测改善"的因果闭环支撑其价值
- LLM 生成的修复建议 80% 指向 prompt 微调,而真实根因分布(检索、工具、路由、温度、few-shot 选择)更广
- 留着就是装饰

如果后续要重新引入,准入门槛是:**被采纳的 suggested_fix 在下次评测中使同一维度分数改善的比例 ≥ 50%**,用 Profile 灰度验证。

### 2.6 信度保证(v2 重写,响应批判 1)

v1 的 "κ ≥ 0.6 + 20-50 条校准集" 既不够严,也没有责任人。v2 改为:

**按维度分级的 κ 目标**

| 维度类型 | 代表维度 | κ 目标 | 校准集规模下限 |
|---|---|---|---|
| 结构化/硬约束类 | 格式遵从、必问项、硬红线 | ≥ 0.85(其实规则层本就不走 κ) | 50 条边界样本 |
| 事实类 | 正确性、业务解答准确性 | ≥ 0.70 | 200 条 / 维度 |
| 语义类 | 相关性、完整性、多轮指代 | ≥ 0.65 | 200 条 / 维度 |
| 软性表达类 | 表达质量、服务语气、品牌合规 | ≥ 0.55(并强制人审占比 ≥ 20%) | 300 条 / 维度 |

**校准集规模下限** 按 κ 的置信区间宽度反推:语义类要把 95% CI 压到 ±0.08 以内,N ≥ 200。v1 的 20-50 条只够做 demo。

**责任与 SLA**
- 每个 Profile 必须指定一名 **Calibration Owner**(领域专家或该 Agent PM),负责校准集的标注、漂移报警的响应
- Judge-vs-Human κ 每周自动回放,任一维度低于目标 → 工单派给 Calibration Owner,**5 个工作日内**必须给出处理结论(扩样 / 调 few-shot / 降级为人审)
- 若连续 2 周未处理,该 Profile 的 verdict 自动降级为 `需人工复核`(不再用于 go/no-go),直到恢复

**Judge-Human 冲突样本的 verdict 降级规则**
- Judge 给出 `不可上线`,但校准集历史上该类样本 Judge-Human 分歧率 > 30% → verdict 自动降档为 `需人工复核`
- 规则硬编码在 orchestrator 里,不走 Profile 配置,防止被关掉

### 2.7 效度保证:线上指标相关性(v2 新增,响应批判 2)

**这是 v2 相对 v1 最重要的新增。** 没有这一节,整个平台就是"用尺子量尺子"。

**Profile 准入门槛**

一个 Profile 要被批准用于 go/no-go 决策,必须通过效度验证:

1. 收集该 Agent 近 N 周(N ≥ 4)的真实线上样本,至少 500 条
2. 用 Profile 对这些样本自动评测,得到每条样本的维度分数和 verdict
3. 和同期的线上指标做相关性分析:
   - **对话类 Agent**:与 CSAT、复问率、人工改写率、转人工率
   - **生成类 Agent**:与采纳率、编辑距离、用户删除率
   - **结构化抽取**:与下游业务系统的校验通过率

**硬门槛**:
- 至少 1 个维度与至少 1 个线上指标的 Spearman ρ ≥ 0.5(或分类 AUC ≥ 0.70)
- `verdict = 不可上线` 样本在线上的差指标率,必须显著高于 `verdict = 可上线` 样本(双样本检验 p < 0.05)

**不通过的 Profile**:可以存在、可以跑报告,但 verdict 字段显示 `效度未验证,仅供参考`,不进 go/no-go 面板。

**效度的持续监控**:
- 每月自动重算一次 Profile 的 ρ / AUC,漂移 > 0.15 触发复评
- Calibration Owner 负责响应,30 个自然日内完成复评,否则降级为"效度未验证"

**这一节回答了"评测有没有用"**:如果答不上,就别上线。

|---|---|---|---|
| Trace 归档(多轮/工具/检索) | ✅ | —— | 直接用 |
| Dataset / Run 管理 | ✅ | —— | 直接用 |
| LLM-as-judge | ✅ | —— | 直接用,只替换 rubric 模板 |
| 人工标注 + span-level feedback | ✅ | —— | 直接用 |
| Prompt / 版本化 | ✅ | —— | 直接用 |

### 3.3 成本与存储(v2 新增,响应批判 7)

**数据量估算(以中型组织为基准)**

| 量级参数 | 估值 |
|---|---|
| 活跃 Agent 数 | 20 |
| 每 Agent 每周评测样本 | 500 |
| 单样本 trace(输入+输出+中间步骤) | 8 KB |
| 单样本 judge 原始响应 | 12 KB |
| **周增量** | 20 × 500 × 20 KB = 200 MB/周 |
| **年增量** | ~10 GB/年 |

**retention 策略**(必配,非可选):

| 数据 | 热存期 | 冷存期 | 归档后 |
|---|---|---|---|
| Trace(输入+输出) | 90 天 | 180 天 | 压缩摘要 + Run 分数 |
| Judge 原始响应 | 30 天 | 60 天 | **删除**,只保留 evidence JSON |
| Evidence JSON(locator + criterion) | 永久 | —— | —— |
| 校准集样本 | 永久 | —— | —— |

**LLM 调用预算**

- **级联的真实节省约 20-30%**,不吹"一个数量级"
- **Profile 必填字段**:`monthly_judge_budget_usd`,创建 Profile 时强制填写(有默认值 $50 / Profile / 月,可调)
- 超 80% 告警,超 100% 该 Profile 的新 run 自动降级为"仅规则层 + 断言层",LLM 证据抽取暂停
- 年度总预算:20 个 Profile × $50 × 12 = $12,000,向管理层明确

## 四、冷启动与采纳路径(v2 用数字重写,响应批判 3)

### 4.1 明确责任人和人时预算

**新增角色:Methodology Lead(方法论顾问)**
- **FTE**: 1.0,冷启动 6 个月满编,之后 0.5 维持
- **职责**:主持诊断工作坊、审核 Profile、治理场景包、维护校准集规范
- **为什么必要**:没有这个角色,工作坊产出的判据会迅速退化成"回复应当专业准确"这种空话

**新增角色:Calibration Owner(校准负责人)**
- 每个 Profile 一名,由 Agent 所在业务线的领域专家或 PM 兼任
- **时间成本**:每 Profile 每周 2-4 小时(标注新样本 + 响应漂移工单)
- 这是进入 Profile 准入门槛的硬条件:**没有 Calibration Owner 的 Profile,不发放 go/no-go 权限**

### 4.2 冷启动总人时预算

| 阶段 | 动作 | 人时 |
|---|---|---|
| 单 Profile 诊断工作坊 | 3 角色 × 2h + MethoLead 整理 6h | 12 人时 |
| 单 Profile 初始校准集(200 条 × 5 维度) | 标注 200 × 5 × 1 分钟 + 复核 | 30 人时 |
| 单 Profile 效度验证(线上 500 条跑分 + 相关性分析) | 数据准备 + 分析 | 10 人时 |
| **单 Profile 冷启动总成本** | | **~50 人时** |
| 6 个月目标:10 个活跃 Profile | | **500 人时 ≈ 3 FTE-月** |

**这个数字必须让管理层看到。** v1 全文没有这个数字,是方案被打回的主要原因之一。

### 4.3 6 个月北极星指标

| 指标 | 6 个月目标 | 测量口径 |
|---|---|---|
| 活跃 Profile 数 | ≥ 10 | 过去 30 天有 ≥ 1 次 run |
| 通过效度验证的 Profile 数 | ≥ 6 | ρ ≥ 0.5 或 AUC ≥ 0.70 |
| WAU(周活跃评测用户) | ≥ 15 | 过去 7 天登录且跑过 run |
| 团队渗透率 | ≥ 3 个业务团队每周 ≥ 1 次回归 | 按 project_id 去重 |
| 平均校准集规模(语义维度) | ≥ 200 条 | 抽样检查 |
| Calibration Owner 工单 SLA 达标率 | ≥ 80% | 5 工作日内响应 |
| 争议池翻转率(扣分被标"不同意" / 总扣分) | ≤ 15% | 衡量 judge 质量 |

**不达以上任何一项,6 个月复盘时要给出原因**,否则 Phase 3 延期。

### 4.4 三阶段路径(在数字约束下重写)

**Phase 1 · Langfuse 落地 + 单点引爆(0-6 周)**
- 部署 Langfuse 自托管实例
- 写 v2 Extension Layer 最小版本:Profile schema + 断言引擎骨架 + 3 条硬红线规则
- 选 1 个争议最大的 Agent 跑完整诊断工作坊,产出第一个 Profile
- 做效度验证:拿线上 500 条样本,算 ρ,如果不过 0.5 就回炉调整判据
- 交付物:该 Agent 每周 1 份评测报告 + 1 份效度报告,进 go/no-go 会

**Phase 2 · 场景包 + 粘贴即用(6-14 周)**
- 补齐 3 个场景包(客服、知识库问答、结构化抽取),每个场景包含可裁剪的维度模板 + 判据示例 + 红线样本
- 关键设计:场景包**不承诺"5 分钟开箱即用"**,改为承诺"5 分钟拿到初稿报告,预计需要 1 周迭代才能达到效度门槛"。v1 的"浅易用 vs 深定制"矛盾由此解决:场景包是起点不是终点
- 再接入 5 个 Agent,每个都走完整的"工作坊 → 校准 → 效度验证"流程

**Phase 3 · 工作流嵌入 + 治理(14 周+)**
- CI 集成:prompt/工具配置变更自动跑评测 + diff,挂 PR
- 效度月度回算 + 漂移工单化
- 场景包治理委员会:Methodology Lead + 各业务线代表,每月评审一次场景包变更
- 争议池每周 Owner 轮值处理

### 4.5 采纳设计四条铁律(沿用 v1)

1. 先给结论再给配置
2. 对比优先于绝对分(本次 vs 上次 diff 永远在 UI 最显眼)
3. 扣分可反驳(一键"不同意"进争议池)
4. 定位工具而非监督工具(报告是调试器,不是 KPI)

## 五、关键风险与对策(v2 更新)

| 风险 | 对策(v2 版) |
|---|---|
| **效度验证过不了** | 这是好事,说明 Profile 判据没抓到真问题——回炉重新和领域专家对齐,不允许绕过 |
| **κ 漂移无人响应** | Calibration Owner + 5 工作日 SLA + 连续 2 周未处理自动 verdict 降级,降级规则硬编码 |
| **诊断工作坊依赖 Methodology Lead** | 承认这个依赖,按 1.0 FTE 配齐;同时沉淀"工作坊 SOP 手册",降低单次主持难度 |
| **场景包浅 vs 工作坊深的矛盾** | 场景包明确是起点不是终点,UI 上对"未经效度验证"的 Profile 强水印标识 |
| **Langfuse 不够用** | 扩展层走插件接口,不改 Langfuse 主体;如需替换基座,断言引擎和场景包可迁移 |
| **硬红线覆盖不全,软红线成噪声** | 硬红线覆盖率审计指标(≥ 60%);软红线触发必须走人审,不直接判"不可上线" |
| **suggested_fix 变装饰** | v2 直接删除,不做就是不做;如重新引入需先证明"采纳→改善率 ≥ 50%" |
| **存储成本失控** | retention 分层:judge 原始响应 60 天后删,只留 evidence JSON |
| **预算护栏形同虚设** | Profile 创建时 `monthly_judge_budget_usd` 强制填写,超额自动降级 |
| **团队抗拒额外工作** | CI 自动触发 + Jira 联动,把评测嵌入既有工作流 |

## 六、一句话主张(v2 修订)

Agent 质量评测的终局,是在**已有的开源基座(Langfuse)之上**,加三样东西:**业务断言**让评测能触达真实数据,**场景包**让评测贴着业务语境,**效度验证**让评测自己接受检验。不证明评测分数和线上指标相关,就不允许用它做 go/no-go。不配 Calibration Owner 和 SLA,就不允许 Profile 准入。没有数字的承诺,不写进方案。
