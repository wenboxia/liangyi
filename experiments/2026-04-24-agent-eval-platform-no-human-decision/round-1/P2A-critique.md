1. LLM 裁判的效度论证为零，"一致性检验"这句话撑不起整个产品
方案把大部分软性维度（共情、合规、信息完整度）压在"配置者写 prompt 让裁判模型打分"上，然后用一句"要求配置者上传少量已人工标注样本、相关性低于阈值不允许上线"处理掉信度/效度问题。这里全是未定义量：多少样本算"少量"？20 还是 500？相关性用 Pearson、Spearman、Kappa？阈值是 0.6 还是 0.8？不同维度是否统一阈值？

为什么是问题：这不是实现细节，是整个产品的正当性基础。LLM-as-judge 在细粒度主观维度上与人工相关性不稳定是有大量公开研究的，尤其是"共情""语气"这类。如果阈值定松了，平台输出的就是包装过的噪声；定紧了，绝大多数方案根本上不了线，产品变成一个启动不了的空架子。产品成立与否取决于这个参数怎么调，而方案里没人回答。

2. "配置是 PM 自己写"和"配置需要工作坊陪跑"是同一个产品里的两条相反承诺
一方面说非工程 PM 也能从模板起步改 prompt、自助配置；另一方面在风险缓解里写"首次使用强制走模板 + 线下共创工作坊 + 平台团队陪跑"。这两件事不能同时为真——要么自助工具成立，要么它本质是咨询交付。

为什么是问题：工作坊模式决定了平台的扩张曲线是人肉线性的，不是软件指数的。团队规模没给，但如果每个新场景都要平台团队陪跑一轮，覆盖 5 个业务线以上就崩。更糟的是：一旦"好的方案都是陪跑出来的"成为隐性事实，业务线没有陪跑就不会自己配，平台沦为工单池，不是基座。

3. 和 Langfuse / LangSmith / Promptfoo / Braintrust 的差异没有任何论证
完整功能清单（DAG 执行引擎 + 图形化设计器 + 规则沙箱 + 版本化测试集 + CI 插件 + SDK + 方案市场 + 解释生成层）是一个需要专职小团队常年投入的工程量。市面上开源/商业方案都已经提供 LLM-as-judge、数据集管理、回归对比、自托管、对接自有 Gateway、CI 集成。

为什么是问题：文档里"自建的边际价值"这个问题根本没被回答过一次。唯一隐含的差异是"维度/规则是配置的 + 解释生成层"——这两件事在 Langfuse 上写几百行 evaluator 代码也能做出来。如果要我批复预算，这一章必须写；现在连竞品名字都没出现。默认假设是自建，这违反了"不自建就死"的举证责任方向。

4. "方案变更强制回溯跑历史批次"是一颗成本定时炸弹，且和迭代节奏对着干
防规则漂移的机制是：改方案 → 自动重跑历史批次 → 生成差异报告。早期方案调 prompt 是高频行为（一天十几次），每次回溯如果命中几千条历史样本 × N 条 LLM 裁判规则 = 每次调规则烧一笔钱 + 堵住流水线。

为什么是问题：会直接诱导团队的两种绕过行为——(a) 把历史批次人为限制在很小的范围让回溯便宜（监管失效），或 (b) 把方案改动攒一批再提交（放弃了细粒度演化）。而且差异报告本身需要人看，几千条的 diff 没人读，读了也难判断"这个下降是规则改好了还是改坏了"——你把一个信度问题塞进了另一个需要人工判断的地方。

5. "扣分原因可直接操作"这个核心承诺对 LLM 裁判规则不成立
文档把可操作性当成卖点："看到的不是 4.2 分，而是'规则 3 未通过：未按模板提供退款链接'"。但这个例子是硬断言规则——硬断言天然可操作，不靠平台。真正占大头的 LLM 裁判规则，扣分理由是裁判模型生成的自然语言 reason 字段。

为什么是问题：LLM 生成的 reason 是 post-hoc 解释，和它真正的打分决策之间没有因果关系保证。裁判可能"因为语气太短"给了低分，但 reason 写的是"缺少安抚语句"，工程师照着改了仍然低分。这在业界是已知现象（explanation ≠ rationale）。平台没有任何机制验证 reason 的可靠性，而整个"从感觉不对到第 X 条规则没过"的叙事完全依赖 reason 可靠。这是产品承诺和技术现实的错位。

6. "不提供跨 Agent 总分"被当成原则，但会直接断掉高层使用场景，间接断掉采用率
坚持维度得分只在同方案纵向可比，拒绝给出跨 Agent 横向数字。立场在工程哲学上可辩护，但商业上意味着：老板、总监、资源分配会议上想看的"哪个 Agent 做得好、预算加到哪里"——平台拒绝回答。

为什么是问题：没有管理层的使用场景 = 没有自上而下的推力。文档自己也说"是否作为上线门禁由各业务线自行决定，平台不强推"——合情合理，但叠加"也不给管理层提供抓手"，等于平台失去了所有非自愿的使用压力。剩下只靠 PM / 工程师自愿用。那么回到第 2 条：配置成本还这么高，自愿用的理由是什么？"感觉不对变成规则 3 没过"对一线有吸引力，但不够把配置成本压下去。

7. 适配成本被系统性低估，几个规则类里藏着跨团队协作的硬骨头
四类规则里，硬断言 + LLM 裁判是平台内可闭环的；结构化抽取验证要调业务 API 对账（每个 Agent 一套集成工作），外部计量规则要接入业务指标（转接率、任务完成率——这些埋点从哪来？数据团队排期？），人工抽检对抗 Goodhart 的机制——谁抽、抽多少、分歧听谁的——整段只有一句话。

为什么是问题：文档把"外部计量"和"人工抽检"当成防作弊的硬约束（"强制保留至少一个外部计量维度"），也就是说这两件事不是可选项，是上线门槛。但每个新 Agent 接入都要跟业务系统、数据系统、运营流程做三次对接——这是典型的"前台功能 1 周、后台对接 3 个月"的坑。接入适配复杂度在方案里几乎不存在，而它才是维护负担的大头。

结论倾向：不批。 第 1、3、5 任何一条单独都是阻断性的；1 和 5 共同说明评测信度与可操作性的承诺没有技术支撑，3 说明没论证过自建必要性。需要作者回来重新回答这三个问题再谈。
