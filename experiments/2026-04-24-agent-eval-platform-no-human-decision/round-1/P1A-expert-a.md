Agent 评测平台方案（专家 A 视角）
一、问题定义
团队对 Agent 输出质量的判断停留在主观感受层面，导致两类损失：优化方向缺乏共识，迭代效果无法度量。要解决这个问题，核心不是"让每种 Agent 有一套专属评测"，而是要建立一套跨 Agent 通用、可横向比较的评分体系。只有当不同业务线、不同版本、不同任务类型的 Agent 输出都落在同一把尺子上，平台才具备长期积累的价值——否则每次评测都是一次性动作，沉淀不出资产。

二、核心评分逻辑
我主张采用 "五维统一评分 + LLM-as-a-judge" 作为评测内核。

五个维度固定不变，适用于所有 Agent：

准确性（Accuracy）：事实、数据、逻辑是否正确。
完整性（Completeness）：是否覆盖输入所要求的全部任务点。
相关性（Relevance）：输出是否紧扣用户意图，无冗余偏离。
安全性（Safety）：是否存在违规、泄露、偏见或越权内容。
风格一致性（Style）：语气、格式、结构是否符合目标场景规范。
每个维度采用 0–5 分制，由裁判模型（judge LLM）基于统一 rubric 打分，并给出结构化的扣分说明。总分采用加权求和，权重默认均等，但允许业务方在 Agent 注册时覆盖（如合规类 Agent 可加重 Safety）。

裁判模型固定为同一个强模型版本，所有评测走同一 prompt 模板，确保结果纵向（时间维度）和横向（Agent 之间）可比。

三、系统架构
整体采用四层架构：

接入层：Web 前端 + OpenAPI，支持粘贴输入/输出、批量 CSV 导入、CI 调用。
评测引擎层：核心的 Judge Orchestrator，负责分发到五维评分器。
裁判模型层：统一调用 judge LLM（封装在内部 Gateway，版本锁定）。
数据层：评测记录库（输入、输出、分数、理由、元数据）+ 分数时序库，支持看板查询。
四、关键模块
Rubric 管理模块：维护每个维度的打分细则、示例、反例。Rubric 是平台的"宪法"，变更需走评审流程。
Judge Orchestrator：将一次评测拆成 5 次并行的 judge 调用，聚合结果，处理重试与一致性校验（同一样本多次打分方差过大时触发复评）。
报告生成器：输出结构化报告——总分、雷达图、每维扣分项列表、改进建议。
基准集管理：沉淀跨 Agent 共用的黄金测试集，用于回归与版本对比。
对比看板：支持 Agent A vs Agent B、同一 Agent v1 vs v2 的差异可视化，这是"可比性"价值的落地出口。
校准模块：定期用人工标注样本校准裁判模型，监控 judge 漂移。
五、部署形式
第一阶段：内部 SaaS，部署在公司 K8s 集群，接入内部模型 Gateway，面向 PM 和工程师开放。
第二阶段：提供 SDK 与 CI 插件，让 Agent 上线前必须跑通评测门禁（如总分 < 3.5 阻断发布）。
第三阶段：开放自定义权重与子 rubric，但五个主维度不可变，以保住通用可比性。
六、风险点
裁判模型偏见：judge LLM 自身可能有风格偏好或事实错误。缓解：固定版本、定期人工校准、关键场景双 judge 交叉。
Rubric 过于通用导致区分度不足：某些垂直任务（如代码生成）在五维上都 4 分以上但实际不可用。缓解：允许注册子维度作为补充信号，但不进入主分。
分数通胀与漂移：长期使用后裁判越打越高。缓解：用固定黄金集做月度体检。
成本：每次评测 5 次 LLM 调用，批量场景开销显著。缓解：缓存 + 小模型预筛 + 抽样评测。
团队接受度：业务方可能抗拒"被打分"。缓解：前期只做观测不做门禁，用数据说话后再推强制。
这套方案的底层信念是：没有统一标尺，就没有真正的迭代。平台的价值不在于评得多准，而在于评得一致。
