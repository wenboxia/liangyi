# Agent 评测平台

## 一句话产品定位

一个把"业务方对 Agent 输出的质量判断"翻译成可执行、可解释、可沉淀的评测规则的工程基座——不是自动打分机，而是团队共识的落地平台。

## 目标使用者与使用场景

核心用户是上线了 Agent 的产品经理与工程师。典型场景有三：

- **单次诊断**：PM 拿着一组"看起来不对"的对话粘贴进来，想知道"到底哪里不对、扣在哪一条规则上"，然后拿着诊断报告去找对应的 prompt / 工具 / 数据问题。
- **版本迭代**：工程师改完一版 Agent，想验证改动是否真的带来质量提升，以及是否在别的维度悄悄退步。需要批量跑、需要 v1 vs v2 的差异视图。
- **上线前把关**：新 Agent 接入时，要求跑通所属场景的评测方案，作为是否具备上线资格的结构化依据——不是靠 demo 现场试几个例子拍脑袋。

我们不服务"跨 Agent 横向打榜"。让客服 Agent 和代码 Agent 的分数出现在同一张表上，本身就是一个没有业务含义的操作，平台不提供这种误导性的可比性。

## 核心评分机制与维度

产品底层信念：**评估维度不是预设的，是配置的**。每个 Agent 类型对应一个评测方案，方案由若干维度构成，每个维度直接对齐一条业务目标——客服场景可能是"合规性 / 共情表达 / 信息完整度"，代码场景可能是"功能正确性 / 接口契约 / 异常覆盖"。维度之下是规则，规则才是最小执行单元。

规则分四类，可在方案中自由组合：

1. **硬断言规则**：输出必须包含某字段、禁止出现某措辞、必须符合 JSON Schema。结果二元，未通过即扣分并短路后续。
2. **LLM 裁判规则**：由配置人编写一段评估 prompt，明确告诉裁判模型"你是 XX 场景的验收员，按以下标准打分并说明原因"，返回结构化的 `score + reason`。这是大多数软性质量判断的承载形式。
3. **结构化抽取验证**：从输出中抽取实体（订单号、金额、SQL），调用业务 API 对照真实状态。
4. **外部计量规则**：接入业务指标（如人工转接率、任务完成率），作为评分输入。

报告形态是**多维诊断面板**而非单一总分。每个维度下列出规则通过 / 未通过清单，每条未通过规则高亮对应输出片段并展开裁判推论。团队看到的不是"4.2 分"，而是"合规维度 · 规则 3 未通过：未按模板提供退款链接；指向对话第 4 轮"。优化方向不需要解读。

我们刻意**不提供一个默认的跨 Agent 总分**。维度得分只在同一方案、同一版本谱系内纵向可比。需要聚合视图时，由方案配置者自己定义汇总方式，平台不替业务做这个决定。

## 系统形态与接入方式

轻量分层架构，评测逻辑与执行分离：

- **接入层**：Web 前端 + OpenAPI + CI 插件。前端覆盖粘贴单次评测、批量 CSV、看板；OpenAPI 与 CI 插件支持 Agent 发版流水线自动触发评测。
- **方案配置层**：评测方案、维度、规则、权重的管理与版本控制。每个方案带关联的测试集，方案变更强制回溯跑历史批次并生成差异报告，阻止规则静默漂移。
- **执行引擎层**：解析方案生成 DAG，硬断言优先执行、失败短路；LLM 裁判调用并行；所有调用异步留痕。裁判模型对接公司内部 LLM Gateway，版本可配置但推荐锁定。
- **解释生成层**：将规则命中结果拼装成自然语言扣分说明，关联原始输出片段。
- **数据层**：评测方案库、执行记录库、测试集库。

关键模块中真正决定产品成败的是两个：**评测方案设计器**和**规则调试沙箱**。设计器提供图形化拖拽与内置模板库（客服对话、代码评审、RAG 问答等），非工程人员也能从模板起步改 prompt；沙箱允许单条规则试跑，实时看到裁判返回的原始 JSON 和扣分原因。没有这两个，配置式评测会死在"不知道自己配的东西到底管不管用"上。

另外提供**内部评测方案市场**，成熟方案作为模板发布，其他业务线替换 prompt 里的具体业务约束即可复用结构，让评测规则像代码一样被沉淀和复用。

部署形态：第一阶段单 Docker 容器内网部署，内嵌轻量数据库与规则沙箱，硬断言与结构化验证零外部依赖；对接公司 LLM Gateway 作为裁判。Agent 输入输出不出内网。第二阶段提供 SDK 与 CI 插件，把评测嵌入发版流程。是否作为上线门禁由各业务线自行决定，平台不强推——强推门禁会在团队还没信任评测之前就把产品推向对立面。

## 关键风险与边界

- **配置惰性**：团队会期待"粘进去就能评"的零配置体验，现实是好评测必须有人把业务判断写清楚。缓解：首次使用强制走场景模板路径，配套线下"评测方案共创工作坊"而非纯工具交付，让第一批方案由平台团队陪跑产出。
- **LLM 裁判偏见**：未经校准的 prompt 容易系统性偏袒长回答、礼貌措辞、结构化格式。方案设计器内建一致性检验：要求配置者上传少量已人工标注样本，平台计算裁判与人工的相关性，低于阈值不允许上线。
- **规则腐化**：业务目标变了但方案没跟着变。强制方案版本化并绑定测试集，修改方案必须重跑历史批次生成差异报告；长期未更新的方案在看板上降权展示。
- **过度拟合规则**：团队为了分数做表面功夫而忽视真实体验。通过两条硬约束对抗：一是强制保留至少一个"外部计量规则"维度（真实业务指标无法作弊）；二是保留"人工抽检"维度，平台随机采样强制人工过一遍，防止规则集合本身塌缩成局部最优。
- **跨 Agent 可比性缺失**：这是选择的代价，不是 bug。需要跨 Agent 对比时，提供的不是数字，而是"两个方案的规则结构并列视图"，让使用者自己判断是否在比较同一件事。
- **成本**：一次评测可能触发多次 LLM 调用。通过硬断言短路、裁判结果缓存（相同输入输出哈希命中直接返回）、以及批量场景下支持小模型预筛，控制在可接受范围。

平台的价值不在于评得多准，在于让团队把"感觉不对"变成"第 3 条规则没过，原因是 X"。能做到这一步，优化方向和迭代量化就都有了。
