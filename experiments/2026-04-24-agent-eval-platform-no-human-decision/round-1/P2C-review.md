方向漂移：从"共识平台"到"标注—窄问题系统"
v1 是什么：一个把业务方的软性质量判断翻译、沉淀、复用的工程基座与组织工具。关键词是"团队共识的落地平台"。核心资产是方案库、规则调试沙箱、内部评测市场；核心采纳路径是"评测方案共创工作坊 + 陪跑"；核心信念是"评估维度不是预设的，是配置的"，PM 配 prompt、写 score + reason，通过方案版本化 + 强制历史回溯 + 外部计量 + 人工抽检来对抗腐化与 Goodhart。平台自己是一个自洽的分层系统。

v3 是什么：一个建在 Langfuse 之上、以窄问题 + 人工标注 + 引用原文为核心的诊断产品。裁判只许输出二元或三档序数，必须引用完整子句，否则降级；规则分 Gate / Observe / Experimental 三级；上门禁要过 κ ≥ 0.6 或 ρ ≥ 0.7 的信效度 gate；背后是 CSV 模板、跨线标注池、3–5 工作日 SLA、季度回归集轮换、契约测试、回滚预案。自建层缩到三件——设计器、诊断视图、看板——其余托付给 Langfuse。

单独看都合理、叠加起来让方向走偏的几次调整：

禁 0–10 自由打分 + 强制窄问题 + 强制引用原文——每一条都在提升可核对性。但 v1 里最典型的场景是"共情表达""合规性"这种软判断，而在 v3 的 lint 里它们恰好是反例。核心承载形式被悄悄换掉了。
引入信效度 gate + 跨线标注池 + 标注 SLA——让门禁站得住脚。但也把"平台能否运转"的根基从"业务方会不会配规则"改成了"标注链路是否通畅"。
规则三级制为了给快速迭代留口子——合理。但它和 gate 叠加后的现实是：大多数规则会长期停在 Experimental，Gate 变成少数，产品的中位使用形态从"上线把关"退回到"单次诊断"。
基础设施交给 Langfuse——省工程量。但 v1 里决定产品成败的"沙箱""方案市场""CI 插件""SDK"要么改名、要么淡出、要么变成 Langfuse 能力。自建侧还剩多少独立产品形态？
外部计量从强制改为可选、工作坊改为 1–2 次 pairing——降低摩擦。但这是把 v1 中两条原则性防线（业务真实指标兜底、组织共创）都降了级：反 Goodhart 退守到人工抽检，采纳退守到模板资产。
漂移的样貌：

从"翻译业务判断" → "编译窄问题 + 标注证据"
从"团队共识的工程基座" → "Langfuse 上的诊断 + 看板层"
从"组织工具（陪跑、沉淀、市场）" → "计量工具（κ、标注池、校准、漂移告警）"
从"业务真实指标兜底" → "人工抽检兜底"
从"上线把关 + 版本迭代 + 单次诊断三场景并重" → "单次诊断最顺、门禁最费劲"
每一步修改都回应了一个真实批评，每一步也都换掉了 v1 的一部分内核。方向从"让团队把感觉不对说清楚的共识平台"漂到了"让裁判判断经得起统计学检验的标注驱动诊断系统"——

这是想要的方向吗？
