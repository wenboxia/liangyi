# idea.md (v4)

## 产品定位

一套以证据为核心的商家刷单风控智能体——通过规则引擎、可解释模型与行为序列模型三层判决，配合专为一线风控员设计的证据化工作台，替代资深风控员的日常批量判别工作，让每一次"定刷单"都能经得起商家申诉、监管问询、合规审计。

**本文档范围**：智能体本身的判别机制、产品功能、发布策略、预算依据。项目对人员结构的影响（转岗通道、再培训、劳动法合规）由平行的 HR/OCM 方案承载，合规披露与法务流程由平行法务方案承载，本文档依赖但不覆盖。

## 目标使用者 / 被影响方

**直接使用者**：
- **一线判别员**：从"逐单扒六维度数据"转为"灰区案件三选一决策 + 大客案件深度复核 + 新模式上报"。工作台产品承诺见下文。
- **黑产情报小组**（保留、扩编）：新作弊模式发现、规则迭代、对抗样本挖掘。对抗黑产的核心人力，明确不在 FTE 替代范围内。
- **风控产品与模型团队**：规则 DSL 编辑、模型回训、基线监控。一线员工不编写 DSL、不涉及代码。

**被影响方**：平台商家（误判直接影响经营，大客/连锁/高 GMV 商家一律走强制深度人工复核）、消费者（搜索决策质量）、合规商家（公平曝光）、黑产刷单团伙（主要对抗对象，以日级周期反推系统边界）。

## 核心机制与判断逻辑

核心立场：**可解释性是风控的承重结构**。判决主干必须是可还原证据的规则与可解释模型；黑盒端到端模型只做辅助感官；LLM 完全不上在线判决链路。

### 三档分流

| 分档 | 占比（目标） | 处置方式 |
|------|------|------|
| 黑白区（规则分与 GBDT 分同时 ≥ 高阈值，或同时 ≤ 低阈值） | 55%~65% | 系统直接处置，事后抽检 |
| 灰区（单侧高分 / 双侧中分 / 两分背离） | 25%~35% | 智能体预组织证据，人工三选一 |
| 大客区（头部商家 / 连锁品牌 / 高 GMV / 历史争议） | 5%~10% | 强制深度人工复核，系统只做建议 |

"同向"的明确定义：规则分与 GBDT 分同时进入高置信区间（判定刷单）或同时进入低置信区间（判定正常），两者结论一致方可自动处置。两分背离一律进灰区。

### 判决管线

**第一段：结构化证据提取**。六维度（订单、用户、商家、设备、支付、评价）特征由特征中台统一维护与版本化。

**第二段：分层打分**。规则引擎负责显式经验沉淀与高确信拦截；GBDT 负责灰区边界判别，SHAP 输出 Top 贡献特征；商家行为序列 Transformer 作为**离线辅助信号**，对灰区做补充风险分与注意力高亮，**不在在线链路上**、不参与毫秒级判决。

**第三段：报告生成**。LLM 仅在运营工作台**异步**生成自然语言证据摘要。**LLM 不在在线判决链路上、不贡献风险分、失败时降级为模板化结构报告。**

规则与可解释模型是主干，序列模型是辅助感官，LLM 是秘书与讲述者。拒绝端到端黑盒直接定案——不是技术洁癖，是业务硬性要求。

## 一线工作台

这是智能体面向一线员工的主产品界面，功能承诺如下：

- **灰区三选一**：① 确认刷单 ② 驳回嫌疑 ③ 升级专家复核。无"挂起"选项，避免积压。
- **规则版本锁定**：案件进入判别视图的瞬间快照当时规则与模型版本，后续热更新不影响进行中的案件；顶栏显示"当前适用版本号"。
- **多标签批量处理**：最多 10 个并发标签页，报告本地缓存预加载；网络抖动时显示缓存版本并置灰操作按钮。
- **可疑新模式上报**：一键触发，自动携带当前案件证据流转至情报小组。
- **一键合规报告导出**：PDF + JSON 双格式，含完整证据链、规则命中、GBDT 分与 SHAP Top N、序列模型高亮、判别人决策与理由、版本号、时间戳。应对监管问询直接下载，不需手动拼截图。
- **降级字段一致**：LLM 失败的模板报告字段结构与正常报告严格一致，不需两边对照填表。

**判别责任的产品级保证**：每份报告自带"证据 hash + 摘要版本号 + 生成参数"。事后复核时可精确还原当时摘要内容——若摘要存在事实错误或关键证据遗漏，可追溯至具体摘要版本并触发复盘。这是产品契约，是申诉复核的技术前提，也是员工与产品之间的可审计边界。

## 系统形态 / 接入方式

**在线链路**：订单落库与评价发布节点，Flink 流处理 → 特征查询 → 规则引擎 → GBDT，毫秒级返回风险分。全程**无 LLM**。

**离线链路**：T+1 对活跃商家跑行为序列模型，产出灰区候选清单与注意力热力。

**持续学习回路**：人工复核结论、申诉结果、新模式上报全部回流样本库。规则支持日级热更新；GBDT 按周回训；序列模型按月回训，对抗样本持续注入。主动学习模块基于模型置信度熵主动挑选最不确定的样本推送人工标注。

## 发布策略：Shadow Mode 与放量门槛

**Shadow mode 并行运行 3 个月**。系统独立跑一套不进入处置链路的判决用于比对，**不占用一线员工工时**；**shadow 期间"人-系统不一致"仅用于系统校准，不作为个人绩效输入**——这不是员工福利，是校准数据质量的必要条件：员工若担心被扣分而选择"跟系统一致"以求保险，校准就失败了。

**放量门槛**（硬性，低于即回滚）：
- 与资深风控员（5 年以上经验、Phase 0 选定基准组）的黑白区一致率 ≥ 97%
- 灰区误伤率（处置后申诉成立率）≤ 现有人工基线的 1.2 倍
- 大客案件 100% 人工，不纳入自动处置统计
- 分组公平性指标（地域、品类、商家规模的误伤率差异）未触红线

**Phase 0 基线测量 2 个月**，对当前人工判别做抽样标注与一致性测量。**没有基线就没有上线。**

## 预算依据与交付节奏

**假设基数**（Phase 0 实测后修订）：一线 FTE 约 N 人，日均案件量约 M 万。

**节省路径**：黑白区 60% × 100% 替代 ≈ 0.60N；灰区 30% × 单案耗时目标压缩 60%~70% ≈ 0.18~0.21N；大客区 10% 不动。合计目标释放 **55%~70% FTE**，成本回收周期 **6~8 季度**（含建设期 4~6 季度）。早期版本曾出现"人均日处理量提升 3~4 倍"的说法，数学推不通，已撤回；整体人效提升按 shadow 实测公布，不预承诺。

**交付节奏**（18~24 月跨团队工程）：

| 阶段 | 周期 | 产品侧交付物 |
|------|------|------|
| Phase 0 | 0~2 月 | 人工基线测量、特征口径清单、规则 DSL 原型 |
| Phase 1 | 2~8 月 | 特征中台 v1、规则引擎、GBDT 打分服务、在线 Flink 链路、一线工作台 v1 |
| Phase 2 | 8~14 月 | Shadow mode 上线，行为序列模型离线训练与灰区辅助信号接入，A/B 框架，漂移熔断 |
| Phase 3 | 14~20 月 | 放量至黑白区全自动处置，LLM 报告生成上线（异步、可降级），主动学习回路 |
| Phase 4 | 20~24 月 | 大客通道与申诉闭环打磨，FTE 释放目标达成 |

任一阶段指标低于基线，回退至上一阶段。

**外部前置条件**（由平行方案承载，本文档依赖而不承担）：HR/OCM 的转岗与再培训方案、法务对《算法推荐管理规定》披露流程的会签、数据团队埋点版本对齐。任一缺失都会阻塞本项目，但不是本文档的交付物。

## 关键风险与边界

**误伤的合规与舆情成本**。大客/连锁强制人工；每次自动处置向商家明示"算法自动化决策 + 证据链 + 申诉路径"；48h 申诉 SLA 从商家提交起算，智能体自动分配 + T-12h 自动提醒。

**对抗节奏不对称**。黑产情报小组保留；规则引擎日级热更新 + 小时级监控告警；序列模型月级回训 + 对抗样本持续注入。立项明确：替代执行岗，不替代模式发现岗。

**模型偏见**。敏感属性去偏训练，分组公平性指标纳入放量门槛（后台监控，不打扰一线）。

**数据口径漂移**。特征中台每个特征配分布监控，漂移超阈值熔断下游依赖。

**实施复杂度**。按 Phase 分阶段立项、每阶段独立验收、每阶段可回滚。

**人机责任边界**。系统只替代重复性判别执行。高风险品类、大客商家、跨区域团伙案、历史争议商家、监管问询案件——始终强制人工决策。责任的产品级保证（证据 hash + 摘要版本号）见"一线工作台"章节；进一步的岗位责任划分由员工手册与 HR 流程承载，本文档不展开。

## 回退日志

本版依据 P2C《方向漂移暴露报告》。核心判断：P2C 的主语漂移指控成立——v3 读起来更像"55%~70% FTE 替代项目及其组织影响"，而不是"风控智能体产品方案"。v4 将主语收回到"风控智能体"本身，产品定位段显式声明文档范围，HR / 合规 / 法务压缩为外部约束。

**判断标准**：改动是否直接改变产品的做法、界面或发布策略——是则保留为产品内容，否则压缩为外部约束引用。

### 主语校正（对 P2C 最直接的回应）

v3 事实上把主语从"风控智能体"漂到"风控智能体落地项目及其组织影响"。v4 主语收回到"风控智能体"本身，并在产品定位段显式声明文档范围，把 HR / 合规 / 法务排除为外部约束。

读者测试：若只读正文，v4 应给出"这是风控产品文档"的答案，不再给出"这是 HR + 合规 + 工程综合立项"的答案。

核心判别机制（规则 + GBDT + 序列模型 + LLM 报告）与 v1 本质一致，结构上回到 v1 的重心分布；一线工作台与责任的产品级保证是 v1 没展开但确实属于产品的部分，在 v4 中以产品语言保留，不借 HR 语言。
