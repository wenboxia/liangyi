# 场景级 Meta-Observations · 2026-05-23 投资 Skill 本体完整跑

> 跑完本场景后追加的方法论级观察。未到本体修订门槛——记录,不修订。

---

## 1. 本体跑的"决策密度"远高于变种

本场景全程产生 10 个人工决策点(0-8 + P3.1.1 校验后 defer 决策),每个都有理由记录在 `decision-log.md`。对比前三次变种实验(美团 / Agent 评测 / ExamSniper)的纯流程产出,本体的人工决策密度高出一个数量级。

**含义**:本体的成本主要在人(Wenbo)身上,变种的成本主要在 token 上。两者不是同一种工作。Wenbo 在本场景里花的真实时间,远高于变种的体感。这是本体的设计代价——不是缺陷,是它存在的理由。

---

## 2. 2C-rollback 是整个跑里最重要的单次决策

P2C 抓到 v1→v3 的累积漂移(产品身份从"投资助手"漂到"防呆引擎"、推荐功能从核心降为"非核心但保留"、Web Search 从自动降为按需、卫星仓 25%→10%),Wenbo 在决策点 5 做了**大回退**——这是整个 run 里影响范围最大的单次决策。

如果没有 2C-rollback,v5/v5.1 会是一个"通过审查的合规文档"而不是"Wenbo 想要的投资助手"(P2C 原话)。P2C 的"方向漂移诊断"机制兑现了本体设计 ch.8 给它的"linear 打散整合的兜底"角色。

**含义**:scope 轴 divergence(整体 vs 局部)在这次跑里证明价值。fix 步骤的 1-by-1 修订即使每步都合理也会漂——必须有 scope 轴在 v1 与 v3 之间打整体对比的复审机制兜底。

---

## 3. P2D-fix 的架构转向收益超出"修方案"

P2D 第 4 点(token 成本 / 认识 Wenbo 伪命题)在决策点 7 不是被"框架内修方案"消化的——它直接催生了部署架构从"独立对话加载"转向"Claude Project 持久化"+ 自我演化机制(15.x)。

这次架构转向反过来又消化了 P2D 第 1 / 第 3 条(动态 Skill 解长上下文累积错误率、动态 Skill 解"过去封印未来")。**一次 P2D-fix 同时解决了 5 条拆台中的 3 条**,而且不是补丁式的解决,是结构级别的解决。

**含义**:P2D 本体设计 ch.8 把它定位为"质疑整个框架前提"——这次场景兑现了这个定位。**P2D 的最大价值不一定是"否决方向",可能是"逼出架构级转向"**——这是变种(P2D 在 5.2 节通常被处理为"框架内 vs 回 P1"二分判定)看不到的本体特有收益。值得在未来跑里继续观察。

---

## 4. 镜子机制的全链路兑现

P2D 第 2 条(镜子论)在决策点 7 是 verbal 拒绝(Wenbo "AI 是顾问、迭代对话发现问题"),但在锁定前 Wenbo 自己提出了"补结构性镜子" + 走法 B(教科书配置 10.2 保留作镜子参照、当前偏好 10.6 显性化、反方视角 + 季度立场挑战拷打偏好)。然后 v5.1 的反方视角机制在 P3.1.1 校验里被两个独立陌生 AI 实际激活——Opus 4.8 的"FOMO 不是建仓理由"、"内部人在你想进场时在卖"直接打在 Wenbo 偏好本身上。

**含义**:P2D verbal 拒绝 + 锁定前补结构性回应 + 校验兑现,这是本体 P2D-fix 一个有趣的"延迟响应"模式——拆台当时不接受,但锁定前补,校验验证。**P2D 的回应不必发生在 fix 当下,可以发生在锁定边界前**——这一点本体目前没有显式承认,值得记录。

## 5. Skill 类产品的 P3 退化模式复现

本场景在锁定后由 Wenbo 主动指出 P3 不需要 4 工程文档,退化为"转译 + 单盲校验"。这与 2026-05-02 design-style-extractor 场景的 P3 退化完全同构。

**含义**:对于"deliverable 本身是一份 .md 文件"的 idea 类型(Skill / Project CLAUDE.md / 单文件协议等),P3 的 4 工程文档框架是冗余的——它会把 idea 内容用 4 个 framing 重写 4 遍。

第二次复现这个 pattern。**可能值得在 longterm-and-reference.md 标为"Skill 类产品 P3 简化分支"候选**——未到本体修订门槛,但跨场景已出现两次。

---

## 6. P3.1.1 校验暴露了一个本体级 gap:Skill 默认信任 Web Search

Wenbo 在校验里跑了两个旗舰(DeepSeek + Claude Opus 4.8)对同一事实("SpaceX 6/12 是否上市")给出**完全相反的判断**。两个都基于实时 Web Search,都自信,都给细节。

这暴露了一个 Skill 当前没有处理、本体方法论也没有讨论过的 gap:**自动 Web Search 机制依赖单一 AI 的检索能力,对高 stakes 事实(IPO 日期/估值/财报数据)的可信度不足**。

**含义**:这不是这次场景独有——任何依赖 Web Search 作为事实兜底的 Skill / Agent / 系统都有此问题。本体的"divergence"机制(P1/P2 链条用底模坐标跨维度做对抗)在 idea 阶段成立,但 idea 锁定后 Skill 部署在单一底模上时,事实检索的 divergence 不再被 P2 链条覆盖。

**Skill 类产品可能需要在自身写入"高 stakes 事实主源验证"作为运行时纪律,而不是依赖 Web Search aggregation。** Wenbo 选择 defer 这个 gap 到运行中处理,但跨场景如果重复出现,可能值得显式纳入 Skill 类产品的本体讨论。

## 7. P3.1.1 校验的方法论价值被低估

校验在本体协议里只是 P3 的一个"可选"小步骤(Qwen-2 模拟用户)。但本场景里它产出了:

- 校验 Skill 的反方视角机制(镜子破除)是否兑现 → 兑现
- 校验 Skill 的核心承诺("任何 AI 都能立即帮 Wenbo")在两个独立陌生 AI 上是否站得住 → 部分站得住,撑不住"立即"
- 暴露了 9 个 Skill 结构性 gap,其中 5 个是 Skill 真没写的盲区
- 暴露了一个本体级 gap(第 6 条)

**含义**:对于 Skill 类产品,P3.1.1 校验的实质价值远高于本体目前的"可选"定位。**它是 Skill 类产品 P3 的核心步骤,不是可选**——因为它直接检验 Skill 的核心承诺。这可能值得在本体 ch.9 P3 设计里给 Skill 类产品做特例标注。

## 8. decision-log 在批量跑场景里的脆弱性

本场景 Wenbo 在 P1.4 之后选择"批量给 prompt、自己跑完、最后一起看"的模式,导致 decision-log 决策点 2-8 在跑完一周后才补记(从 `我和claude-2的完整对话记录.md` 摘录)。

**含义**:补记是可行的(对话记录质量很高,转换无损),但**补记时已经记不清"当时为什么那么判"的微观心理过程**。decision-log 作为本体核心产物,它的价值有一部分是"决策当时的判断捕捉"——这一部分在批量跑模式下会受损。

这件事在 Claude 第一次提批量风险时被预言过,Wenbo 也接受了这个 tradeoff。**对本体方法论的建议:批量跑模式应作为"灰线"显式记录,标注它在 decision-log 即时性维度上的代价**——使用者自行权衡。

---

## 总结:这次本体跑的不可替代收益

如果只能用一句话描述本体跑相对变种的不可替代价值:

> **本体跑产出的不是一份方案,是一份"经过 Wenbo 在场审视的方案 + 一份决策链记录 + 一份被校验过的镜子破除证据"。** 其中后两份是变种无法产出的。
