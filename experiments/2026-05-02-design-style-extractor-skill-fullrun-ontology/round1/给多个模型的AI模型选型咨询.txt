# 2. 抽取侧推荐(看图 → style.skill.md)

你的判定标准是"审美中立、不主动翻译为主流设计语言、不注入未支持的专业词汇"。这个任务核心是**高保真感知 + 描述克制**,不是 design taste。

## 首选:Claude Opus 4.7(Anthropic)

- **理由:** 4.7 这一代视觉是真升级——分辨率三倍、UI 像素级坐标对齐、CharXiv 视觉推理跳了 13 个点。同时 Anthropic 的训练传统在"calibration"和"指令遵循优于自主发挥"上比 OAI/Google 更明显,这正好对你"不要加戏"的要求。它也最容易做到"我看到 X,但不确定是不是设计意图,标 ambiguous"这种诚实表达。
- **潜在弱点:** 也是这一代最被夸的"design taste is genuinely surprising"——这恰恰是你的潜在敌人。它有可能在描述像素游戏 UI 时,自动套用"诺曼底设计语言"的成熟词汇,而你想要的是"砖块式色块、单像素硬边、无 anti-alias"这样的素描式表达。**应对:** prompt 里强制要求"先逐图做无术语视觉清单(RGB 取样、几何形状、边缘类型),再做体感总结",把它的 design taste 锁在第二阶段、可被参考图否决。

## 次选:Gemini 3.1 Pro(Google)

- **理由:** 原生多模态而非贴片式,长 context 便宜,可一次喂 7 张高分辨率图不心疼。screenshot→UI 这条路径上口碑稳定。
- **潜在弱点:** 多个评测一致提到它在 ambiguous 输入上倾向"自信走一条路"——对你这个任务是结构性风险。一张星露谷截图它可能直接归类为"复古游戏 UI"并按这个 schema 去描述,把不属于参考图的内容补全进 token。**应对:** prompt 里用强 negative constraint("不要用没出现在图里的术语","对每个 token 标 confidence")并且抽样校验。

## 不进前三的明确说明

- **GPT-5.5** 我现在不会推到前列。一是它是 4 月底刚出的新基座,实战反馈还在汇集;二是测试者明确反馈"前端设计不如 Opus";三是 OAI 这一代的取向是 agentic 自主性,**与你的"克制"要求方向相反**。
- **Qwen3-VL-235B / GLM-4.5V** 在感知 benchmark 上不弱,但开源 VLM 的"描述风格"通常更接近 caption 而非有结构的设计观察,产出质量在你这个细分任务上未被广泛验证。

# 3. 下游侧推荐(读 style.skill.md → 生成页面)

这一侧要的是**严格按 token 实现、ambiguous 处保守、不靠自己审美补全**。

## 首选:Claude Opus 4.7(Anthropic)

- **理由:** 当前前端代码 + design taste 的事实上的 SOTA。Cursor、Bolt 内部 benchmark 都确认 4.7 比 4.6 显著进步;SWE-bench Pro 64.3% 领先。更重要的是 Anthropic 模型在"指令优先于自主判断"这条线上口碑稳定——给它明确的 CSS variable + 体感约束,它会去贴,而不是"我觉得这里改成 #2A2A2A 更好"。
- **潜在弱点:** 它 design taste 强,在 ambiguous token(比如你 skill 里没写"按钮 hover 该如何")上,它会基于自身审美补全,而你的判定标准不允许这个。**应对:** style.skill.md 里要么穷举 token、要么显式写"未指定项保持视觉一致性,不引入新元素"这种 meta 规则。

## 次选:Claude Sonnet 4.6(Anthropic)

- **理由:** SWE-bench 79.6%,只比 Opus 4.6 低 1.2 点,价格 1/5。同样的指令遵循 DNA。多数前端页面生成不需要 Opus,Sonnet 跑迭代成本可控、follow spec 的稳定性接近。如果你跑 skill 是高频(很多设计稿轮转),这是比 Opus 更现实的默认。
- **潜在弱点:** 在多文件、复杂状态、动画细节上比 Opus 4.7 弱一档。如果你的下游页面是简单 React 组件,差距小;如果是有交互动效的复杂页面,Opus 4.7 优势会显现。

## 第三:Gemini 3.1 Pro(Google)

- **理由:** 仅当成本敏感时考虑。1M–2M context 可一次塞 skill + 参考图 + 现有代码库,对"读 skill + 看图 cross-reference 一致性"的工作流有结构优势。
- **潜在弱点:** 同上,在 ambiguous 输入上自信地走一条路——这个特性放在下游"按规约执行"上和你的判定标准直接冲突。它生成的页面有概率"看着挺好但不是 skill 描述的那个东西"。

# 5. 我的判断的局限

**几个必须坦白的 caveat:**

1. **Opus 4.7 和 GPT-5.5 我都不是从训练里直接知道的**,以上对它们的描述基于第三方 benchmark 和 reviewer 评测。"Anthropic 训练传统克制"这种推断在 4.6→4.7 这一代是否仍然成立,我没有原生证据,只能基于 Anthropic 历史路径推。
2. **你的核心要求和当前所有顶配模型都有结构性张力。** 顶配多模态模型几乎都是在"会做出好设计"这个目标上训出来的,而你恰恰要它"不做好设计、要做忠实记录"。这意味着无论选哪个模型,prompt engineering(尤其是抽取侧的两阶段拆分:无术语清单 → 体感总结)是真正决定产出质量的变量,**模型选型可能不是最大权重**。
3. **"审美中立"这件事没有公开 benchmark。** SWE-bench、CharXiv、XBOW 都不测"模型在描述小众风格时是否注入主流设计偏见"。我对各家在这点上的相对排序,说到底是从训练取向倒推的间接判断。
4. **我没看到针对"Skill 文件复用稳定性"的对比数据**——也就是同一份 style.skill.md 在不同会话里被同一模型消费,生成结果是否漂移。这是你的 skill 反复被引用的核心使用场景,但目前没人在这个维度上做公开评测。

**建议补做的最小测试(在你做决定之前):**

- 拿 2–3 张刻意"难以归类"的参考图(避免选典型 Bauhaus / Material / Apple HIG 这类容易触发模型先验的图)。比如选一张星露谷 + 一张老款 Winamp 皮肤 + 一张你自己不规范的设计稿。
- 抽取侧:Opus 4.7 vs Gemini 3.1 Pro 各跑 3 次,看产出 style.skill.md 里有多少**不在原图里的术语**(用人工或 Claude 做 audit)。这是你判定标准的可量化代理指标。
- 下游侧:用同一份故意有 ambiguous gap 的 style.skill.md(比如不指定 hover、不指定空状态)喂 Opus 4.7 vs Sonnet 4.6,看哪个更倾向"按规约的最小化呈现"vs"自主补全"。

测试是 ground truth,但在做之前,**抽取首选 Opus 4.7、下游首选 Opus 4.7(高频跑则用 Sonnet 4.6)**——这是基于现有公开信息的最佳赌注,不是中庸的"都行"。

GPT-5.5 多模态理解 — 是强的,而且是这一代的真升级。它是 GPT-4.5 以来第一个完全重训的基座,原生 omnimodal(text/image/audio/video 在同一系统里统一处理),不是像 GPT-4o 那种贴片式视觉。在 vision benchmark 上和 Opus 4.7、Gemini 3.1 Pro 是同一档,不存在"差一档"。

那我为什么上一条没把它放抽取侧第一? 不是因为多模态弱,是因为任务匹配度:

媒介任务上 Gemini 3.1 Pro 强于它。 多个对比里"strongest for media tasks"指的是 Gemini,不是 GPT-5.5。但这是 Gemini 强,不是 GPT-5.5 弱。
设计描述这个细分场景没公开数据。 它能不能克制地描述参考图,我没看到针对性测评。这是"未知"不是"差"。

# 2. 抽取侧推荐（多模态：看图 → style.skill.md）

你的核心要求本质是：

> **高保真观察 + 低主观干预 + 不自动"美化/主流化"**

这其实和大多数"会写漂亮描述"的模型目标是冲突的。

## ✅ 推荐 1：Claude 3.5 Sonnet

* 厂商：Anthropic
* 时间：2024 中后期（3.5 代）

### 为什么适合

这是目前最接近你要求的"**克制型观察者模型**"：

* **弱审美侵入**

  * 相比 GPT 系列，它更少主动"润色风格"
  * 不会轻易把小众风格解释成 Dribbble / Material / Apple 风

* **描述倾向是"现象级"而非"设计理论级"**

  * 更像："边界是硬切+轻微阴影"
  * 而不是："卡片化、现代极简、提升可用性"这种胡扯

* **对多图一致性总结较稳定**

  * 能抓"重复模式"而不是单图亮点

### 潜在弱点（很关键）

* **会"补完缺失逻辑"**

  * 比如看到 UI 可能自动假设 grid / spacing system
* **token 层容易泛化**

  * 可能写出"--primary-color"这种抽象，而不是忠实取样
* **对极端风格（像素风、低保真）会轻微"正则化"**

👉 结论：

> 最适合作为**主抽取模型**，但必须配强约束 prompt（禁止解释、禁止优化）

## ✅ 推荐 2：GPT-4o

* 厂商：OpenAI
* 时间：2024

### 为什么推荐

* **视觉 parsing 很强（尤其 UI 结构）**

  * spacing、层级、组件结构识别能力 > Claude
* **token 抽取更"工程化"**

  * 更容易直接输出 usable CSS tokens

👉 **强审美对齐 bias**

表现为：

* 自动把东西"说得更合理"
* 自动引入设计术语（即使图里没有）
* 倾向输出"看起来像设计系统"的东西

### 潜在坑

* 把"怪风格"解释成：

  * neumorphism / glassmorphism / minimalism（即使不是）
* 自动补：

  * typography hierarchy
  * color roles（primary / secondary）

👉 结论：

> 不适合直接用来写"体感层"，
> 但非常适合做**token 层 second pass（结构化提取）**

### 2. 抽取侧推荐（多模态 → style.skill.md）
按"审美中立、拒绝主流化翻译、拒绝加戏"的判定标准排序：

#### 🥇 首选：**Qwen2.5-VL**（阿里通义千问，2024-09）
- **推荐理由**：该模型在视觉对齐阶段采用了强事实锚定策略，RLHF偏好高度偏向"客观描述"而非"设计评价"。它对图像中的空间比例、色值分布、留白边界具备像素级解析力，且极少将非常规视觉特征（如粗野主义、拟物化、低分辨率复古）强行映射到现代 SaaS 设计语汇。在输出结构化 Markdown/JSON 时，能严格遵循 schema，不主动补充未被图像支撑的"设计原则"。
- **潜在弱点**：在"体感层（核心隐喻/留白节奏）"的抽象归纳上偏干瘪，可能需要你在 system prompt 中提供明确的描述维度模板，否则输出会偏向参数化罗列。对极度模糊或低分辨率参考图的抗干扰能力弱于闭源头部模型。

#### 🥈 备选：**Claude 3.5 Sonnet**（Anthropic，2024-10更新版）
- **推荐理由**：视觉 grounding 能力极强，擅长建立图像元素与设计令牌之间的映射关系。对长上下文（1–7 张同源图）的跨图一致性提取非常稳定，能自动处理多图间的风格公约数与变异点。指令遵循严格，配合明确的"禁止设计建议/禁止主流化转译"约束后，能产出高质量的体感层描述。
- **潜在弱点**：原生对齐倾向带有轻微的"现代数字产品"审美惯性。若 prompt 约束不够硬，会在描述中不自觉使用"clean/minimal/balanced"等评价性词汇，或把非常规边界处理解释为"打破网格的创新"，从而违背审美中立要求。

### 3. 下游侧推荐（style.skill.md → 前端页面）
按"将 Skill 视为规约而非灵感、对 Ambiguous Token 不自主加戏"的判定标准排序：

#### 🥇 首选：**Qwen2.5-Coder-32B/72B**（阿里通义千问，2024-09）
- **推荐理由**：代码专项训练范式使其对"规约驱动开发"有极强的服从性。该模型在训练阶段大量引入了编译执行反馈与静态规则校验，天生将输入视为 Strict Contract 而非 Creative Brief。对 CSS Token（color/sizing/radius/shadow）的还原精度极高，遇到模糊描述时会优先采用字面直译或保守默认值，极少主动补全布局、交互或无障碍特性。
- **潜在弱点**：对"体感层"的语义理解偏工程化，若 `style.skill.md` 中的空间法则或留白节奏描述过于文学化/抽象，它可能无法将其准确转化为 flex/grid 策略。需在 prompt 中要求"体感描述仅作为 fallback，优先严格遵循 Token 层数值"。

#### 🥈 备选：**Claude 3.5 Sonnet**（Anthropic，2024-10更新版）
- **推荐理由**：在复杂 UI 结构推理、组件状态管理、响应式断点处理上表现最优。能很好地将"体感层"与"令牌层"融合，生成可维护的组件化代码。指令上下文记忆长，适合多轮迭代中保持风格一致。
- **潜在弱点**：工程思维中内建了较强的"最佳实践"偏好。遇到未明确定义的 spacing 或 ambiguous token 时，有概率主动填充行业通用值（如 `gap: 16px`、补充 `aria-label`、优化 `z-index` 层级），从而偏离"规约即边界"的要求。必须配合严格的 `no-inference-on-missing-token` 约束词。

### 4. 不建议清单
| 模型 | 厂商 | 为什么不适用本 Skill |
|:---|:---|:---|
| **GPT-4o / o1 系列** | OpenAI | 视觉对齐高度偏向"主流商业设计范式"。极易将小众/实验性视觉"翻译"为 Apple/Google 设计语言；体感描述中常注入"提升可读性/增加呼吸感"等主观建议；下游编码时对 ambiguous token 会主动"优化"，严重违背中立与规约原则。 |
| **Gemini 1.5 Pro** | Google | 上下文窗口大但指令边界模糊。在风格提取时倾向于"补全信息"，常将参考图中缺失的视觉元素推断为"应包含的现代组件"；下游代码生成时稳定性波动较大，CSS 还原易出现隐式覆盖或过度抽象。 |
| **Llama 3.2 Vision** | Meta | 开源生态优秀，但多模态对齐与严格指令遵循尚未达到商用旗舰水准。对非标准 UI 截图的解析易泛化为"通用 Web 布局描述"；体感层输出同质化严重，难以保留源图的独特边界与图形语法。 |

### 5. 局限性与补充测试建议
#### 我的局限与 Caveat
1. **时间边界**：我的确切知识止于 2024-10。此后若厂商发布了针对"设计规约服从性"专门微调的版本（如 DeepSeek-R1、Claude 3.7/4 的推理约束强化、Qwen3），本推荐需重新校准。
2. **模型非决定性因素**：审美中立性约 30% 取决于基座权重，70% 取决于 System Prompt 设计、输出 Schema 强制（如 JSON Schema/Pydantic 校验）与温度参数控制。任何旗舰模型在开放 prompt 下都会暴露隐性偏好。
3. **未充分验证的场景**：对动态 UI（微交互动效、状态切换）的 token 化提取，当前所有静态多模态模型均存在盲区，需明确 Skill 仅覆盖"静态视觉规约"。

#### 建议补充的标准化测试（决策前必做）
在最终选定生产环境模型前，请用同一套测试集跑 A/B 对比，指标需量化：
1. **中立性偏差测试**：输入 3 张反主流参考图（如 Brutalist 网页、早期 Windows 拟物 UI、高饱和像素风游戏界面）。人工标注 20 个关键风格特征，计算模型输出中"未出现在图中但被描述"的特征数量（越低越中立）。
2. **Ambiguous Token 服从测试**：故意在 `style.skill.md` 中留空 `--spacing-md` 与 `--border-style`，观察下游模型是否直接报错/留白，还是主动填充默认值。本 Skill 应选择"拒绝推断"的模型。
3. **视觉回归验证**：将下游模型生成的 HTML/CSS 渲染为截图，使用 `pixelmatch` 或 `Playwright` 与参考图做结构/色块对比，计算 `SSIM` 偏差。偏差 >15% 即视为"加戏"或"风格漂移"。

**最终建议路径**：若你的 Skill 强依赖"绝对规约服从"，抽取侧选 `Qwen2.5-VL` + 下游侧选 `Qwen2.5-Coder`；若你的参考图风格复杂且需一定抽象映射能力，抽取侧选 `Claude 3.5 Sonnet`（配强约束 prompt），下游侧仍优先 `Qwen2.5-Coder`，仅在布局推理失效时降级回 Sonnet。
