# idea-v3.md · 设计风格提炼 Skill

## 一、产品定位

**一个把参考图压缩为"可移植、可复用、可审计"的设计风格 skill 文件的元 skill**——用户在自己的会话里手动引用本 skill，喂入若干张同源参考图，它产出**另一份具备完整 skill frontmatter 的子 skill 文件**，用户后续在前端编码任务里再次手动引用这份子 skill，下游 AI 就能稳定生成与参考图风格一致的界面。

它的产物**不是**一次性界面，**不是**临时提示词，**不是**针对单一风格手写的 skill 集合，而是一个能反复跑、跑出不同风格 skill 的"风格提炼器"。

**本 skill 自己长什么样**：它就是一份标准的 `design-style-extractor.skill.md` 文件——一个带 frontmatter 的 markdown 指令文件，用户拿到手后放进 skill 库，在会话中显式引用即可启动。它的 frontmatter 形如：

```yaml
---
name: design-style-extractor
description: 把若干张同源参考图压缩为一份可复用的 style.skill.md（含设计 token 与风格体感描述）。当用户希望把参考图风格提炼成可在后续会话中复用的设计语言时，由用户手动引用本 skill。
---
```

**关于触发方式**：本 skill 与它产出的子 skill 都由用户手动引用调用，不依赖系统自动触发。description 字段写得好仍有意义（帮助用户在自己的 skill 库里检索定位），但本方案不假装是一个能被 marketplace 系统自动分发的触发型 skill。

## 二、核心机制（输入 → 处理 → 输出）

### 2.1 输入侧

- **图片数量**：**推荐 5–7 张**，是软性建议而非硬性门槛。低于 5 张依然可以跑，skill 会执行，但产物会显式标注"输入样本不足，风格变异边界未覆盖"，让用户自行判断是否补图。极端情况下 1 张也能跑——只是产物的可复现性与覆盖度递减。
- **图片类型推荐覆盖**（不是必须）：
  1. 典型主界面（风格的核心面貌）
  2. 细节或材质特写（按钮 / 卡片 / 图标 / 纹理，承载微观语法）
  3. 状态或边缘场景（hover / 选中 / 弹层 / 空状态 / 极限光照，揭示风格的韧性与破裂点）

  缺类时 skill **不报错、不阻塞**，只在产物里把对应章节的字段标记为"基于有限样本推断"。
- **建议（非强制）**：同一产品同一版本；尽量避免跨产品混搭、拼贴图、带浏览器 chrome 或手机壳的截图；分辨率长边越高越好。允许附一句风格上下文（如"参考《纪念碑谷》的关卡过场"）作为辅助语境。

设计原则：**降低门槛，对真实用户友好**。真实 vibe coder 的常态是手头只有几张随手存的截图，硬门槛只会把人推走。

### 2.2 处理侧

本 skill 是一份 markdown 指令文件，跑在**用户当前会话的当前模型**上——它**没有任何切换模型的能力**。

但模型选择对效果至关重要，因此本 skill 会在文档里给出**模型推荐清单**（首选 / 次选 / 不建议），由用户在跑 skill **之前**自行把会话切换到推荐模型。推荐清单是讨论阶段需要决策的内容（市面上哪些多模态模型在视觉风格识别上最强），最终会作为本 skill 文档的一部分附上。

**双层提取的执行步骤**（skill 指令文件里以编号步骤明确写出，不靠玄学"互相校准"）：

1. **观察阶段**：模型逐张观看用户提供的参考图，不输出任何内容，只在内部建立印象。
2. **体感层产出**：按固定 6 段结构产出体感层内容，每段以章节编号 §1–§6 命名（核心隐喻 / 空间构成 / 色彩光线 / 图形语法 / 排版留白 / 不可触碰边界）。这一步禁止出现任何数值。
3. **令牌层产出**：按固定字段表产出令牌层内容（颜色 / 字体 / 间距 / 圆角 / 阴影 / 组件 / motion / composition / material）。**每个 token 末尾用 `(→ §N)` 单向标注它服务于体感层哪一段**——这是单向标注，不是双向引用，避免字段错乱。
4. **自检阶段**：模型扫一遍完整产物，列出体感层中没有任何令牌引用的段落（提示用户该段可能纯感性、未被骨架承接），以及令牌层中标注为"基于有限样本推断"的字段（提示用户审阅或补图）。

两层各司其职：体感层负责风格的精神内核，令牌层负责可工程化的视觉决策。"体感层防止令牌层退化为色卡复制，令牌层防止体感层飘成无法落地的散文"——通过上面 4 步执行顺序与单向引用机制实现，不依赖模型自由发挥。

### 2.3 输出侧

产物是一份 **`style.skill.md`**，**带完整 skill frontmatter**，可被用户在后续会话中作为子 skill 引用。结构如下：

```markdown
---
name: style-<风格代号>
description: 应用 <风格代号> 风格到本项目的前端页面。当用户在前端编码任务中希望保持本项目设计一致性、或希望模仿 <参考来源> 的视觉语言时，由用户手动引用本 skill。
source_images:           # 字符串数组，本地相对路径或文件名，仅作为元数据记录，不影响下游执行
  - imgs/ref-01.png
  - imgs/ref-02.png
extracted_at: 2026-05-02T14:30:00Z   # ISO 8601 时间戳
---

# 第一部分 · 风格灵魂（体感层）

## §1 核心隐喻
[一句穿透性断言，给出风格的精神内核]

## §2 空间构成法则
[关系性描述：层次嵌套、深度幻觉、视觉重心、非对称平衡]

## §3 色彩与光线的情绪记忆
[散文式描述色彩坡度、暗部态度、高光体温]

## §4 图形与符号的语法
[几何的锐钝、线条的性格、被允许与被禁止的形状]

## §5 排版与留白的呼吸节奏
[文字与留白的体感]

## §6 不可触碰的边界
[绝对违规项清单]

# 第二部分 · 风格骨架（令牌层）

## tokens（machine-readable）
:root {
  --color-primary: #e8b86a;   /* (→ §3) */
  --color-bg: #1a1622;        /* (→ §3) */
  --radius-md: 8px;            /* (→ §4) */
  ...
}

## components / typography / motion / composition / material
[按字段填充，每项末尾带 (→ §N) 单向锚]

## 待补字段
[列出无法从图中确定的字段，供用户审阅、补图或手动指定]
```

**`source_images` 与 `extracted_at` 的格式与作用**：前者是字符串数组，写本地相对路径或纯文件名即可（不要 Base64、不要远程 URL，避免膨胀）；后者是 ISO 8601 时间戳。两者都只是元数据记录，下游模型读取这份子 skill 时把它们当作普通文本注释处理——纯文本模型遇到这两行不会报错也不会去尝试加载图片，因为本 skill 不要求下游具备图像加载能力。如果用户担心元数据干扰特别严格的下游，可以在分发前手动删除这两行，不影响子 skill 主体的可用性。

引用规则只做**单向**：令牌层 token → 体感层段落锚 `(→ §N)`；体感层不反向指向令牌层字段。这样模型在单次生成中只需维持一个方向的对应关系，不会产生双向交叉引用错乱。

去掉了过去版本里的 `confidence: { color: 0.x }` 字段——这种分数是 LLM 凭空写出来的，没有统计基础。"待补字段" 区块也明确定位为给用户审阅的提示清单，不承诺下游模型一定会读它。

## 三、形态选择：万能抽取器，且诚实承认质量天花板

如第一节所述，本方案的形态就是"万能抽取器"——一个 skill，跑一次产出一份风格 skill，**不**做手写具体风格库（纪念碑谷.skill.md / 锈湖.skill.md 这种逐个手写的形态）。这一节回答的是：既然手写专精的质量更高，为什么仍然选万能抽取器？

**先承认质量天花板**：一个真懂纪念碑谷美学的人手写的 skill，几乎一定胜过本 skill 自动抽取出来的版本——因为人手写时融入了"哪些是核心、哪些是噪音、哪些允许变异、哪些是不能动的风格签名"这种判断，而抽取本质是在图里做平均。**专精 > 普适**，这是承认而不是回避。

那为什么仍然选万能抽取器？因为它和手写专精解决的根本不是同一类问题：

1. **覆盖**：手写库永远滞后——用户想要的下一个风格库里大概率没有；万能抽取器当场能跑。
2. **杠杆**：万能抽取器跑一次就产出一份手写专精形态的文件，用户可以拿这份初稿继续手改、精雕——它是手写专精的**起点**而不是替代品。
3. **维护**：手写库随参考产品迭代会僵化；万能抽取器重新喂新图就能更新。
4. **个性化**：用户的参考图组合往往是自己的私人审美剪贴板，手写库里不可能有现成的。

所以本 skill 的定位是：**给"没有手写专精 skill 可用"的绝大多数情况提供一个比凭空喂图更结构化的起点**。它的天花板低于手写专精，但它的下限高于直接喂图凭运气。

## 四、与"直接喂图给 GPT Image / Gemini 多模态"的差异

本 skill 的不可替代价值在四点：

1. **可移植**：style.skill.md 是纯文本，可注入任何 System Prompt、任何后续会话。下游消费时——令牌层（颜色、字号、间距、组件 token）在**任何**模型上都有效，包括纯文本 LLM；体感层（隐喻、关系性描述）在带视觉联想能力的下游模型上发挥最大价值，在弱视觉模型上**有损但不归零**——比喻语言依然能给出方向，只是损失一部分张力。卖点是"令牌层全场景有效 + 体感层强场景增益"，而不是"两层在所有下游都满血"。
2. **可重复**：同一份 skill 跑 100 次 coding，token 与体感坐标都是同一份，结果可比对、可 diff。直接喂图每次输出都不一样。
3. **可审计 / 可手改**：用户能 diff 两份 skill、能把 `--color-primary` 改掉、能在体感层把"暮光橙灰"改成"晨雾蓝白"。图片改不动。这一点也呼应第三节——本 skill 的产物是**用户后续手动精修的起点**，可改性是核心特性。
4. **可缓存 / 可组合**：skill 一次抽取、N 次复用；CSS variables 直接进 Tailwind config / theme / Storybook。每次重新喂图的方案在大型项目里成本不收敛。

一句话：**直接喂图是一次性即兴；本 skill 是把风格固化成可工程化、可继续修改的资产**。

## 五、适用场景边界

**适用**：

- 模仿既有产品的 2D UI 视觉风格
- 给 vibe coding 项目锁定设计语言、跨多个页面保持一致性
- 有强烈视觉立场、可被压缩为一种"美学主张"的风格化产品——艺术游戏、叙事交互页面、独立品牌站、氛围型数字体验
- 用户希望拿到一份**可继续手改的初稿**，而不是寻求即时一次性产出

**不适用 / 效果递减**：

- 3D 场景美术、关卡设计、角色设计、插画生成、品牌 VI 重塑
- 以信息密度和操作效率为核心的 B 端后台
- 用户其实只想要"好看"而没有具体参照物——本 skill 不负责生成审美主张
- 下游 AI 完全不具备视觉联想能力时，体感层效益打折（但令牌层仍然有效；`source_images` 等元数据字段不会引发报错）
- 对风格保真度有极致要求的场景——此时应该用本 skill 的产物作为初稿，再人工精修，或干脆找懂这个风格的人手写一份专精 skill

## 六、验证回路

第一版必然不完美。验证逻辑分两层：

**作者自验（早期闭环）**：

1. **抽取**：拿一组参考图（如纪念碑谷过场截图 5–7 张）跑 skill，得到 `style-monument-valley.skill.md`
2. **复现**：把这份 skill 喂给下游 AI（Claude Code 或 vibe coding 工具），让它生成一个全新页面（登录页 / 列表页 / 设置页）
3. **对照三问**（每问都给可执行判定）：
   - **风格识别度**：陌生人单看生成结果，能不能说出"这像纪念碑谷"？判定方式见下文外部盲测。
   - **非机械复制 vs 风格跑偏**：通过两条可执行规则同时判定——
     - **非机械复制**：生成页面的布局结构、文案、组件组合不能与任何一张原参考图构成"换皮级复刻"（即把原图任一张的元素位置、文字内容直接搬过来即可生成的相似度），需是新页面但带同种风格语言。
     - **未跑偏**：用 skill 中令牌层 8 项核心 token（主色 / 背景色 / 字体家族 / 行高档 / 圆角档 / 阴影档 / 栅格列数 / material 类型）作为基准，生成产物中实际呈现的对应视觉决策 ≥7 项与 skill 一致即视为风格未跑偏。两条同时满足才算通过。
   - **可改性**：手动把 skill 里某个 token 改值（如 `--color-primary` 改色相），下游产物对应位置颜色随之变化，且变化方向可预测（不是改主色却变了别处），即视为通过。
4. **回归用例**：维护 3–5 套固定参考图集（写实 / 低多边形 / 极简 / 暗黑解谜 / 田园），每次 skill 迭代跑一遍同一组用例，对比前后产物。

**外部验证（公开发布前的准入门槛）**：

作者自审是早期开发的必要环节，但不足以证明 skill 真的 work。在公开发布前，至少需要：

- **盲测样本**：召集 3–5 位非作者背景的设计 / 前端从业者，让他们看生成结果（不告知是哪个风格的提炼），独立写出"这像什么风格"。命中率作为风格识别度的客观指标。
- **基线对照**：同一组参考图，分别用"直接喂图"和"本 skill"两条路径生成同一个页面，让盲测样本投票哪条路径产物更接近原风格。本 skill 至少需要在多数场景里不输于直接喂图。
- **失败信号公开**：如果某类风格（例如手绘 / 高度叙事性的 motion）盲测明显不及格，在 skill 文档里明确标注它不适用，而不是隐藏。

验证标准只有一条：**用户拿着 skill.md 而不是图片，下游 AI 也能稳定做出"对的味道"**——并且这个"稳定"经得起非作者样本检验。

**本次响应的卡点（按出现顺序）**：

- **元 skill 自身格式不明**：第一节增补一段"本 skill 自己长什么样"，给出 `design-style-extractor.skill.md` 的 frontmatter 示例。

- **第三节 A vs B 与第一节定位脱节**：第三节开头改为承接式表述，从"既然第一节已说选万能抽取器，这一节回答为什么"展开，不再以并列候选方案对比开场。
- **`source_images` 在纯文本下游会不会报错**：2.3 与第五节同步说明——元数据被当作普通文本注释，不会报错，必要时可手动删除。
