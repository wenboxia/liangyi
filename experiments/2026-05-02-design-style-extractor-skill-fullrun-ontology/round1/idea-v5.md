# idea-v5.md · 设计风格提炼 Skill

## 一、产品定位

**一个把参考图压缩为"可移植、可复用、可审计"的设计风格 skill 文件的元 skill**——用户在自己的会话里手动引用本 skill,喂入若干张同源参考图,它产出**另一份具备完整 skill frontmatter 的子 skill 文件**,用户后续在前端编码任务里再次手动引用这份子 skill,下游 AI 就能稳定生成与参考图风格一致的界面。

它的产物**不是**一次性界面,**不是**临时提示词,**不是**针对单一风格手写的 skill 集合,而是一个能反复跑、跑出不同风格 skill 的"参考图风格压缩器"。

**目标用户**:vibe / web coder——希望快速把"我喜欢的这种风格"变成可复用的开箱即用风格定案,在后续前端开发里反复引用、保持页面间一致性。本 skill 不与设计师手写的专精 skill 竞争质量上限,也不为专业设计场景做兼容设计。

**本 skill 自己长什么样**:它就是一份标准的 `design-style-extractor.skill.md` 文件——一个带 frontmatter 的 markdown 指令文件,用户拿到手后放进 skill 库,在会话中显式引用即可启动。它的 frontmatter 形如:

```yaml
---
name: design-style-extractor
description: 把若干张同源参考图压缩为一份可复用的 style.skill.md(含设计 token 与风格体感描述)。当用户希望把参考图风格提炼成可在后续会话中复用的设计语言时,由用户手动引用本 skill。
---
```

**关于触发方式**:本 skill 与它产出的子 skill 都由用户手动引用调用,不依赖系统自动触发。description 字段写得好仍有意义(帮助用户在自己的 skill 库里检索定位),但本方案不假装是一个能被 marketplace 系统自动分发的触发型 skill。

## 二、核心机制(输入 → 处理 → 输出)

### 2.1 输入侧

- **图片数量**:**推荐 5–7 张**。低于 5 张依然可以跑,skill 会执行,但产物会显式标注"输入样本不足,风格变异边界未覆盖",让用户自行判断是否补图。极端情况下 1 张也能跑——只是产物的可复现性与覆盖度递减。
- **图片类型推荐覆盖**(不是必须):
  1. 典型主界面(风格的核心面貌)
  2. 细节或材质特写(按钮 / 卡片 / 图标 / 纹理,承载微观语法)
  3. 状态或边缘场景(hover / 选中 / 弹层 / 空状态 / 极限光照,揭示风格的韧性与破裂点)

  缺类时 skill **不报错、不阻塞**,只在产物里把对应章节的字段标记为"基于有限样本推断"。
- **建议(非强制)**:同一产品同一版本;尽量避免跨产品混搭、拼贴图、带浏览器 chrome 或手机壳的截图;分辨率长边越高越好。允许附一句风格上下文(如"参考《纪念碑谷》的关卡过场")作为辅助语境。

**门槛设计原则**:以推荐替代强制。推荐项标明"为什么推荐",让用户在质量与便利之间自己取舍——而不是用硬门槛把样本不齐全的用户拒之门外。

### 2.2 处理侧

本 skill 是一份 markdown 指令文件,跑在**用户当前会话的当前模型**上——它**没有任何切换模型的能力**。

但模型选择对效果至关重要,因此本 skill 会在文档里给出**双侧模型推荐清单**——抽取侧(跑本 skill 的多模态模型)与下游侧(消费 style.skill.md 的编码模型),都倾向于推荐**审美中立、主见不过强**的模型,避免模型自己的隐式审美偏好把风格带偏。**具体首选/次选/不建议清单是讨论阶段需要决策的内容**,最终会作为本 skill 文档的一部分附上。

**双层产出的真实价值——结构化 + 人类可审计**:

- **体感层**(关系性语言):承载风格的精神内核——核心隐喻、空间法则、色彩气质、图形语法、留白节奏、不可触碰边界。
- **令牌层**(结构化字段):承载可工程化的视觉决策——颜色、字体、间距、圆角、阴影、组件状态、composition、material。

诚实交代:**两层之间不存在 LLM 级的"互相约束"机制**。LLM 是自回归生成,体感层和令牌层只是同一次前向传播里先后采样出来的 token 序列,它们看起来配套是因为模型被训练成让它们看起来配套,不是因为有跨层校准的因果机制。所以双层结构的真实价值不是"模型自己保证一致",而是:

1. **结构化产出**:让产物有固定形态,便于下游消费(令牌层进 Tailwind/theme,体感层进 prompt 注释)。
2. **人类可审计**:用户能看到每个 token 末尾的 `(→ §N)` 锚号,可以挑出"这个 token 找不到对应体感法则"或"这段体感描述没有任何 token 承接",进而手动修正。审计主体是用户,不是模型自己。

执行流程仍是 4 步,但目的是产出结构化文本,不是产出"自我校准过的"文本:

1. **观察阶段**:模型逐张观看用户提供的参考图,不输出任何内容,只在内部建立印象。
2. **体感层产出**:按固定 6 段结构产出体感层内容,每段以章节编号 §1–§6 命名(核心隐喻 / 空间构成 / 色彩光线 / 图形语法 / 排版留白 / 不可触碰边界)。这一步禁止出现任何数值。
3. **令牌层产出**:按固定字段表产出令牌层内容。每个 token 末尾用 `(→ §N)` 单向标注它对应体感层哪一段——这个锚号是给**人类审阅用的索引**,不是模型保证的因果链。
4. **可审计自检**:模型扫一遍完整产物,列出体感层中没有任何令牌引用的段落、令牌层中标注为"基于有限样本推断"的字段。这一步本质上还是模型自己审自己,可信度有限,真正的把关在用户手里和外部盲测里。

### 2.3 输出侧

产物是一份 **`style.skill.md`**,**带完整 skill frontmatter**,可被用户在后续会话中作为子 skill 引用。结构如下:

```markdown
---
name: style-<风格代号>
description: 应用 <风格代号> 风格到本项目的前端页面。当用户在前端编码任务中希望保持本项目设计一致性、或希望模仿 <参考来源> 的视觉语言时,由用户手动引用本 skill。
source_images:           # 字符串数组,本地相对路径或文件名,仅作为元数据记录,不影响下游执行
  - imgs/ref-01.png
  - imgs/ref-02.png
extracted_at: 2026-05-02T14:30:00Z   # ISO 8601 时间戳
---

# 第一部分 · 风格灵魂(体感层)

## §1 核心隐喻
[一句穿透性断言,给出风格的精神内核]

## §2 空间构成法则
[关系性描述:层次嵌套、深度幻觉、视觉重心、非对称平衡]

## §3 色彩与光线的情绪记忆
[散文式描述色彩坡度、暗部态度、高光体温]

## §4 图形与符号的语法
[几何的锐钝、线条的性格、被允许与被禁止的形状]

## §5 排版与留白的呼吸节奏
[文字与留白的体感]

## §6 不可触碰的边界
[绝对违规项清单]

# 第二部分 · 风格骨架(令牌层 · 静态可见)

## tokens(machine-readable)
:root {
  --color-primary: #e8b86a;   /* (→ §3) */
  --color-bg: #1a1622;        /* (→ §3) */
  --radius-md: 8px;            /* (→ §4) */
  ...
}

## components / typography / composition / material
[按字段填充,每项末尾带 (→ §N) 单向锚]

## 待补字段
[列出无法从图中确定的字段,供用户审阅、补图或手动指定]

# 第三部分 · 推断字段(基于风格语境,非图像可视提取)

## motion(性格描述,不出具体数值)
[用气质描述动效:如"过渡应当缓慢、带漂浮感,缓动曲线偏向 ease-out 类的回弹收尾"。
不给具体的 cubic-bezier 参数与 duration 数值。
明确标注:本字段不是从静态截图提取,是模型基于风格语境的合理推断,用户可保留、可手改、可整段删除,不影响主体令牌层的可用性]
```

**为什么 motion 单独成区、且只给性格不给数值**:5–7 张静态截图里物理上不包含 motion 信息——交互响应曲线、缓动性格、页面过渡时序,这些东西照片捕捉不到。如果在令牌层凭空写出具体的 `cubic-bezier(0.34, 1.56, 0.64, 1)` 与 `duration: 240ms`,本质上是模型在训练数据里见过类似风格的描述后补出来的幻觉,与用户上传的参考图没有因果关联。所以本 skill 的处理是:**把动效气质放进推断区描述、不出数值,把"是从图里提的还是基于语境推的"这件事在文档结构上让用户一眼看清**。

**`source_images` 与 `extracted_at` 的格式与作用**:前者是字符串数组,写本地相对路径或纯文件名即可(不要 Base64、不要远程 URL,避免膨胀);后者是 ISO 8601 时间戳。两者都只是元数据记录,下游模型读取这份子 skill 时把它们当作普通文本注释处理——纯文本模型遇到这两行不会报错也不会去尝试加载图片。如果用户担心元数据干扰特别严格的下游,可以在分发前手动删除这两行,不影响子 skill 主体的可用性。

引用规则在执行上是**单向**(令牌层 token → 体感层段落锚 `(→ §N)`),目的不是让模型互相约束,而是**给用户一个可审阅的索引**——能让用户判断每个工程化决策是否有体感法则的归宿。

去掉了过去版本里的 `confidence: { color: 0.x }` 字段——这种分数是 LLM 凭空写出来的,没有统计基础。"待补字段" 区块也明确定位为给用户审阅的提示清单,不承诺下游模型一定会读它。

## 三、形态选择:参考图风格压缩器,而非手写具体风格库

如第一节所述,本方案的形态就是**参考图风格压缩器**——一个 skill,跑一次产出一份风格 skill,**不**做手写具体风格库(纪念碑谷.skill.md / 锈湖.skill.md 这种逐个手写的形态)。

**承认覆盖率上限**:本 skill 不主张能"完整提取"参考图风格,主张的是把**静态可见的风格特征**(颜色配比、字体气质、间距密度、圆角档、阴影档、图形语法、空间幻觉感、留白节奏等)压缩成结构化文本,覆盖率粗估在 70–80% 之间。无法压缩的部分包括动态特征(交互响应、页面过渡、缓动性格)、信息架构展开逻辑、以及任何只能在使用中体验到、不在静态截图里出现的风格签名。这些不是本 skill 的承诺范围。

**与手写专精的关系**:一个真懂某种美学的人手写的 skill,几乎一定胜过本 skill 自动压缩的版本——因为人手写时融入了"哪些是核心、哪些是噪音、哪些允许变异、哪些是不能动的风格签名"这种判断。本 skill 不与手写专精竞争质量上限,服务的是**没有手写专精 skill 可用、又想要风格一致性**的绝大多数 vibe coding 场景。

那为什么仍然选这条路、不做手写专精库?

1. **覆盖**:手写库永远滞后——用户想要的下一个风格库里大概率没有;参考图风格压缩器当场能跑。
2. **维护**:手写库随参考产品迭代会僵化;参考图风格压缩器重新喂新图就能更新。
3. **个性化**:用户的参考图组合往往是自己的私人审美剪贴板,手写库里不可能有现成的。

## 四、与"直接喂图给 GPT Image / Gemini 多模态"的差异

本 skill 的不可替代价值在四点——核心主张是**把风格固化成可工程化的资产**:

1. **可移植**:style.skill.md 是纯文本,可注入任何 System Prompt、任何后续会话。下游消费时——令牌层(颜色、字号、间距、组件 token)在**任何**模型上都有效,包括纯文本 LLM;体感层(隐喻、关系性描述)在带视觉联想能力的下游模型上发挥最大价值,在弱视觉模型上**有损但不归零**。卖点是"令牌层全场景有效 + 体感层强场景增益"。
2. **可重复(范围明确)**:**在固定下游模型 + 固定 skill 的组合下**,token 与体感坐标是同一份,产物可比对、可 diff。跨下游模型不主张可重复——不同下游模型对同一份 CSS 变量的隐式审美偏好不同,会带来视觉决策方差,这是已知风险(详见第七节)。
3. **可审计 / 可手改**:用户能 diff 两份 skill、能把 `--color-primary` 改掉、能在体感层把"暮光橙灰"改成"晨雾蓝白"。图片改不动。可改性是资产可演化、可个性化的核心特性。
4. **可缓存 / 可组合**:skill 一次抽取、N 次复用;CSS variables 直接进 Tailwind config / theme / Storybook。每次重新喂图的方案在大型项目里成本不收敛。

一句话:**直接喂图是一次性即兴;本 skill 是把风格固化成可工程化的资产**。

## 五、适用场景边界

**适用**:

- 模仿既有产品的 2D UI 视觉风格
- 给 vibe coding 项目锁定设计语言、跨多个页面保持一致性
- 有强烈视觉立场、可被压缩为一种"美学主张"的风格化产品——艺术游戏、叙事交互页面、独立品牌站、氛围型数字体验
- vibe / web coder 直接复用产物作为开箱即用的风格定案

**不适用 / 效果递减**:

- 3D 场景美术、关卡设计、角色设计、插画生成、品牌 VI 重塑
- 以信息密度和操作效率为核心的 B 端后台
- 用户其实只想要"好看"而没有具体参照物——本 skill 不负责生成审美主张
- 下游 AI 完全不具备视觉联想能力时,体感层效益打折(但令牌层仍然有效;`source_images` 等元数据字段不会引发报错)
- 对动态特征(动效缓动、交互响应、页面过渡)有保真度要求的场景——这些不在本 skill 覆盖范围内
- 对风格保真度有极致要求的场景——此时建议直接找懂这个风格的人手写专精 skill

## 六、验证回路

第一版必然不完美。验证逻辑分两层:

**作者自验(早期闭环)**:

1. **抽取**:拿一组参考图(如纪念碑谷过场截图 5–7 张)跑 skill,得到 `style-monument-valley.skill.md`
2. **复现**:把这份 skill 喂给下游 AI(Claude Code 或 vibe coding 工具,**固定到推荐清单里的同一个下游模型**),让它生成一个全新页面(登录页 / 列表页 / 设置页)
3. **对照三问**(每问都给可执行判定):
   - **风格识别度**:陌生人单看生成结果,能不能说出"这像纪念碑谷"?判定方式见下文外部盲测。
   - **非机械复制 vs 风格跑偏**:通过两条可执行规则同时判定——
     - **非机械复制**:生成页面的布局结构、文案、组件组合不能与任何一张原参考图构成"换皮级复刻",需是新页面但带同种风格语言。
     - **未跑偏**:用 skill 中令牌层 8 项核心 token(主色 / 背景色 / 字体家族 / 行高档 / 圆角档 / 阴影档 / 栅格列数 / material 类型)作为基准,生成产物中实际呈现的对应视觉决策 ≥7 项与 skill 一致即视为风格未跑偏。两条同时满足才算通过。
   - **可改性**:手动把 skill 里某个 token 改值(如 `--color-primary` 改色相),下游产物对应位置颜色随之变化,且变化方向可预测,即视为通过。
4. **回归用例**:维护 3–5 套固定参考图集(写实 / 低多边形 / 极简 / 暗黑解谜 / 田园),每次 skill 迭代跑一遍同一组用例,对比前后产物。
5. **下游模型方差测试**:同一份 skill,在推荐清单的首选 + 次选下游模型上各跑一遍同一个页面,对比视觉决策方差。方差过大则需要重新评估下游模型推荐清单。

**外部验证(公开发布前的准入门槛)**:

作者自审是早期开发的必要环节,但不足以证明 skill 真的 work。在公开发布前,至少需要:

- **盲测样本**:召集 3–5 位非作者背景的设计 / 前端从业者,让他们看生成结果(不告知是哪个风格的提炼),独立写出"这像什么风格"。命中率作为风格识别度的客观指标。
- **基线对照**:同一组参考图,分别用"直接喂图"和"本 skill"两条路径生成同一个页面,让盲测样本投票哪条路径产物更接近原风格。**这条仅作为下限基线**——本 skill 必须在多数场景里不输于直接喂图,否则直接证伪。
- **失败信号公开**:如果某类风格(例如手绘 / 高度叙事性的 motion)盲测明显不及格,在 skill 文档里明确标注它不适用,而不是隐藏。

**成功标准是绝对线,不是相对线**:本 skill 要做到的是"用户拿着 skill.md 而不是图片,下游 AI 也能稳定做出'对的味道'"——这是终极目标,做不到 skill 就没价值,做到了才是真资产。"不输于直接喂图"只是必要条件 / 底线。两条标准并存:相对线判定底线(不及格直接证伪),绝对线判定合格(做出对的味道才是合格)。

## 七、已知风险与应对

本 skill 在产品哲学层面有三个已知风险,不回避、不掩盖,在此明确写出与对应应对:

**风险 1 · 双层耦合在 LLM 内部不是真约束,只是表层关联**

LLM 是自回归生成,体感层与令牌层是同一次前向传播里先后采样出来的 token 序列。它们看起来配套是因为模型被训练成让它们看起来配套,不存在跨层因果约束。每个 token 末尾的 `(→ §N)` 锚号也不是模型在真的溯源,只是在生成一个看起来像溯源的字符串。让同一个模型既产出又自检,等于让同一个偏见做二次确认,自检阶段的可信度有限。

**应对**:不把"两层互相约束"作为产品哲学卖点。双层结构的真实价值落在**结构化产出格式 + 人类可审计**——锚号是给用户看的索引,真正的把关发生在用户审阅、外部盲测、回归用例三个环节,而不是模型内部的"自我一致性"。文档里明确告诉用户:看到锚号请自己判断,不要默认它一定对。

**风险 2 · 同一份 skill 在不同下游模型上有审美方差**

CSS 变量本身没有语义。`--color-primary: #e8b86a` 在不同下游模型里会被解释为不同的"主色"——一个模型把它用在主按钮和关键 CTA,另一个模型可能把它用在背景或边框;一个模型基于它推断的同色系周边决策(辅色、hover 态、阴影色)可能完全不同。这不是用户输入端的方差,是下游模型隐式审美偏好导致的方差,更隐蔽、更难排查。

**应对**:文档里附**双侧模型推荐清单**(抽取侧 + 下游侧),倾向于推荐审美中立、主见不过强的模型;"可重复"这一卖点的语义明确收窄到**"在固定下游模型 + 固定 skill 组合下可重复"**,不再 claim 跨下游模型一致;验证回路里增加"下游模型方差测试"环节,把方差暴露给用户而不是藏起来。**具体哪些模型放进首选/次选/不建议清单,是讨论阶段的开放议题。**

**风险 3 · 静态截图无法承载动态特征,motion 等字段是基于风格语境的推断,不是从图里提取**

5–7 张静态截图里物理上不包含交互响应曲线、缓动性格、页面过渡时序等动态信息。如果在主令牌层凭空写出具体的 `cubic-bezier(...)` 与 `duration: Xms`,本质上是模型在训练数据里见过类似风格的描述后补出来的幻觉,与用户上传的参考图没有因果关联。

**应对**:输出结构里把 motion 单独移到"推断字段(基于风格语境,非图像可视提取)"分区——只用气质描述写出动效性格,**不出具体数值**。文档结构上让"哪些是从图里提的、哪些是基于语境推的"对用户一目了然。用户可以保留、可以手改、可以整段删除推断字段,不影响主体令牌层的可用性。同时第三节"覆盖率上限"那段也明确写出:本 skill 主张的是 70–80% 静态可见特征压缩,不是完整风格抽取。
